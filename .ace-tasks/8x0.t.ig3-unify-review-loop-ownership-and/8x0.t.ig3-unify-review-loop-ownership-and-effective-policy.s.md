# Unify review loop ownership and effective policy

## Behavioral Specification

### User Experience

An operator runs one delivery review stage and gets exactly one verified repair cycle with explicit policy provenance and stable session identity.

### Expected Behavior

- ace-review owns campaign/findings/dispositions and the review workflow; ace-assign invokes that stage and consumes its outcome. Eliminate overlapping automatic verify/apply stages without disabling explicitly selected standalone feedback tools.
- Inventory and verify all findings before any repair. Apply independent required findings as one batch; separate commits only for demonstrated dependency ordering. Run affected verification once per complete batch, then resolve with proof.
- Display effective policy and provenance for package, user, project and explicit invocation settings using the existing configuration cascade. Project-specific stricter delivery gates remain enforceable; contradictions cannot silently select whichever workflow an agent last read.
- Resolve the working repository, owning worktree and artifact store explicitly. A session created under shared-root storage must remain consumable from the owning worktree without broadening unrelated path access. Every list/show/verify/resolve operation retains the same session/campaign identity.
- Schedule task/changelog/docs completion before final review/release evidence. Capture the selected delivery outcome and scoped authorization at start; honor valid existing authorization without asking again. Missing authority blocks the specific action, never becomes implicit consent.
- Preserve provider-neutral delivery ownership from qkb; this task adds review-stage integration, not a replacement forge workflow. Nervus-specific changes are a separate consumer, not implicit edits to that repository.

## Interface Contract

The existing assignment review step consumes a campaign ID, effective-policy description and result receipt. Public status shows the stage owner, source of each effective policy, current session/worktree, required authorization and remaining actions. Feedback operations accept/use the explicit session from the completed round. Recovery resumes the same stage rather than reinvoking already completed effects.

All interfaces described here are proposed acceptance contracts, not a claim of currently installed functionality. Draft usage scenarios are in `ux/usage.md` in this task directory.

## Readiness decisions: ownership and consumer integration

- **Verified starting point:** the current ACE work-on-task preset already has one canonical review-pr stage and composition rules acknowledge that review includes repairs. The duplicate ownership observation comes from Nervus's override. Preserve the working canonical path; add explicit ownership/validation to prevent duplicate automatic repair stages in composed/overridden workflows rather than performing an unnecessary rewrite.
- **Dependency:** qkb is still pending and owns final provider-neutral delivery consumers. R2 depends on qkb and R1, and updates those delivered consumers once, not parallel GitHub-only replacements. Being pending here means specification-ready, not executable before dependencies finish.
- **Responsibility:** ace-review owns the campaign contract and dispositions; the authorized execution agent/service performs code repairs under that workflow. The review CLI must not gain a second autonomous implementation engine. ace-assign remains owner of step attempts, retries and accepted receipts.
- **Consumers:** inspect/update the canonical review workflow/skill source, feedback CLI, assignment review-step catalog, composition rules, task/batch/fix recipes and delivered qkb workflow consumers. Inventory each existing consumer as changed or already compliant. Keep standalone feedback commands usable without reinserting them automatically after a review stage that already owns repair.
- **Session boundary:** automated campaign feedback requires explicit campaign/session binding, never the most-recent-session fallback. Interleaved sessions for two PRs must not cross-select findings. Standalone interactive commands retain their documented behavior. Validate repository identity, common Git ownership, session source and target before consuming shared-root artifacts.
- **Artifact boundary:** qjl's verifier continues to reject traversal/symlink escapes and external receipt artifacts. Materialize an immutable, checksum-verified session/result snapshot inside the owning worktree for receipt consumption, retaining bound source provenance. Reading a same-repository shared store does not authorize arbitrary external paths or changes to another worktree. No patch to Nervus-specific receipt scripts is part of this task.
- **Policy:** expose resolved values and their config/workflow origin, distinguishing search thresholds, execution budgets and consumer acceptance gates. Existing config precedence resolves ordinary values; never silently discard the explicit consumer gate. Incompatible constraints (for example required rounds above the permitted execution cap) fail preflight before a provider call, rather than guessing which instruction wins.
- **Recovery:** reuse complete, verified stage results; partial provider/repair work resumes from its actual evidence, not prose. An interrupted uncertain external action follows existing attempt reconciliation and is not retried automatically. A new head preserves campaign history while invalidating stale receipts.
- **Authorization:** consume existing scoped actor/outcome authorization from the trusted execution boundary; do not introduce a user-controlled approved boolean or a new approval service. Resolve required lifecycle permissions before final stages, preserve refusals, and never treat elapsed time as approval in this workflow.
- **Finalization:** run required metadata preparation before final evidence, but do not require task status done before its implementation acceptance criteria are proven. If a consumer requires a status/archive commit, prepare it after substantive verification and then obtain the applicable final receipt. Later edits invalidate applicable evidence; preserve the recorded campaign rather than restarting every scope.

### Modes and failure outcomes

Assignment composition/preflight supports dry-run without provider execution or repair. Empty/ambiguous subject, conflicting owners, unavailable artifact store and wrong-session identity fail with the responsible stage and reason. Structured status remains parseable in quiet/verbose modes and exposes remaining actions. No force or implicit latest-session lookup may bypass campaign binding in automation. A review stage result is neither merge authorization nor a deployment instruction.
