## Canonical reservation and explicit cancellation — repair candidate

Use the existing attempt journal as the sole reservation owner. A fresh request_review reserves its candidate's review slot in the same CAS that records the request. Direct assign_review must check the same slot inside its existing mutation callback: only the internal delegation for that exact active request may consume a delegated reservation. A fresh direct assignment reserves that slot itself. Neither direct nor delegated assignment may replace a still-active request/assignment, including an accepted approval, without explicit cancellation. Candidate replacement makes prior reservations inapplicable to the new exact candidate; stale events never acquire authority over it. Replay is historical response only and does not restore a cancelled reservation.

Add fixed bodyless cancel_review with exact params mapping_id,assignment_id,attempt_id,head,candidate_generation,review_event_id,expected_generation and caller-supplied outer mutation ID. review_event_id is the canonical request event digest for delegated work, or assign_review event digest for a direct assignment. Resolve it inside the same journal at CAS time; arbitrary IDs, another attempt/candidate or a child assignment incorrectly presented as a delegated root refuse. Admission requires either the original request's stable reviewer principal (current mapped reviewer role, UID/GID/groups and independence, so same-principal restart can cancel) or the actual original launcher admitted by the existing launcher identity check. Direct assignments have no requesting principal and can be cancelled only by their authenticated original launcher. No UID or role flags grant access.

Cancellation records a canonical revocation referring to that exact reservation and any derived assignment. It does not terminate a process, prove death, undo an executed review, remove reports or release a runtime/workspace scope. Existing first request/assignment replies are immutable. Returned current metadata includes the cancellation event, commit and generation; review_status reports this separately. Exact cancellation replay reauthenticates its caller and returns the original reply. New cancellation of an already cancelled or foreign reservation refuses; caller must observe rather than invent a second cancellation.

Every fresh assign_review, candidate export for review, accept_review and approved_review consumer reauthenticates the same active reservation from canonical events. In particular accept_review must repeat this check inside its receipt mutation CAS. If cancellation wins, a late upload/accept cannot restore approval; if acceptance wins first, the later cancellation revokes its use for future operations but does not rewrite already accepted history. Candidate/generation changes never trigger automatic cancellation, re-request or provider restart. All races use the existing journal CAS; there is no external reservation cache or new generation mode.

The request-to-assignment generation rule deliberately preserves ordinary JournalMutation semantics. If other work advances the attempt before the original Driver assigns review, review_status reports the retained request and current generation, and the operator explicitly cancels with that observed generation before requesting again. A further generation race refuses again. This is observable conflict recovery, not silent refresh or a timeout-derived no-effect assertion.

Required controlled regressions: intervening mutation between request and assignment; same-principal restarted requester cancellation; unauthorized/foreign cancellation; direct assignment racing a delegated request; cancellation racing assignment/export/acceptance; exact old request/assignment replay after cancellation; and accepted approval becoming unusable after cancellation while historical evidence stays intact. These map to SC2 and SC3. This repair candidate requires independent review before promotion.
