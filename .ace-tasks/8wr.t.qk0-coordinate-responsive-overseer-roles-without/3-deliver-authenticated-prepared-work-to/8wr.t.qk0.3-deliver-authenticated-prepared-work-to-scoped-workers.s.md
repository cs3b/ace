# Deliver authenticated prepared work to scoped workers

## Objective and observable result

A protected worker consumes exactly the reviewed prepared task subtree accepted for its original attempt. The numeric reservation must constrain actual assignment driving, rather than merely label canonical ownership while a fixed worker reads unrelated mutable local input. This is a vertical source prerequisite of qk0.1; qk0.0 canonical inventory is independent of this child; qk0.3 depends on its delivered inventory before extending its row contract. No new execution journal, launcher, listener, privilege, or caller-selected executable is introduced.

## Prepared work contract — revised candidate

### Preparation and selected work

Preparation uses TaskAssignmentCreator, AssignmentExecutor and their existing managed preset/queue owners. Select one reviewed leaf task or explicit reviewed leaf subtask: its status is pending or in-progress, needs_review is false, and no unresolved review questions remain. The unique matching taskref-bearing fork root in the prepared queue is the numeric scope, including every initial descendant. For the default preset this is the task child under 010, not global 000 onboarding or the whole 010 fan-out. Missing/multiple roots, an expanding parent with several leaves, or a non-fork root refuses before registration. Every selected initial step must be pending; completed steps/reports cannot stand in for preparation. Global onboarding/delivery remains qkb.1's explicit downstream responsibility.

Capture the exact UTF-8 generated job, initial selected step files and reviewed instruction context after managed materialization. Initial step records have closed `{number, filename, bytes, sha256}` fields; `bytes` is a positive Integer byte count, and the content is a separate artifact file. Numbers are canonical numeric scope strings sorted by integer component order; filenames must equal StepFileParser.generate_filename(number, parsed name), with no separators/traversal. Freeze all frontmatter except the progress fields below, including taskrefs, source/workflow/skill targets, parent, fork settings and instructions. Reject duplicate numbers, unsupported YAML values/duplicate keys, or an inconsistent parent/task/project association. Preparation does not rerun an existing progressed assignment to manufacture pending input.

Changed live task/dependency files after acceptance cannot alter consumed context. Explicit lifecycle writes (e.g. marking the selected task done) still use the maintained task owner and do not replace the snapshot. Step instruction text/source targets are already materialized; protected driving must use the captured materialization rather than resolve a workflow/skill again from current source.
