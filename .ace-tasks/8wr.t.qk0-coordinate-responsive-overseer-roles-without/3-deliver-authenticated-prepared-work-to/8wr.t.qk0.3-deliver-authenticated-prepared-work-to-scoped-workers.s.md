# Deliver authenticated prepared work to scoped workers

## Objective and observable result

A protected worker consumes exactly the reviewed prepared task subtree accepted for its original attempt. The numeric reservation must constrain actual assignment driving, rather than merely label canonical ownership while a fixed worker reads unrelated mutable local input. This is a vertical source prerequisite of qk0.1; qk0.0 canonical inventory is independent of this child; qk0.3 depends on its delivered inventory before extending its row contract. No new execution journal, launcher, listener, privilege, or caller-selected executable is introduced.

## Prepared work contract — revised candidate

### Preparation and selected work

Preparation uses TaskAssignmentCreator, AssignmentExecutor and their existing managed preset/queue owners. Select one reviewed leaf task or explicit reviewed leaf subtask: its status is pending or in-progress, needs_review is false, and no unresolved review questions remain. The unique matching taskref-bearing fork root in the prepared queue is the numeric scope, including every initial descendant. For the default preset this is the task child under 010, not global 000 onboarding or the whole 010 fan-out. Missing/multiple roots, an expanding parent with several leaves, or a non-fork root refuses before registration. Every selected initial step must be pending; completed steps/reports cannot stand in for preparation. Global onboarding/delivery remains qkb.1's explicit downstream responsibility.

Capture the exact UTF-8 generated job, initial selected step files and reviewed instruction context after managed materialization. Initial step records have closed `{number, filename, bytes, sha256}` fields; `bytes` is a positive Integer byte count, and the content is a separate artifact file. Numbers are canonical numeric scope strings sorted by integer component order; filenames must equal StepFileParser.generate_filename(number, parsed name), with no separators/traversal. Freeze all frontmatter except the progress fields below, including taskrefs, source/workflow/skill targets, parent, fork settings and instructions. Reject duplicate numbers, unsupported YAML values/duplicate keys, or an inconsistent parent/task/project association. Preparation does not rerun an existing progressed assignment to manufacture pending input.

Capture the selected task and the transitive declared task dependencies through the maintained task/bundle owners, retaining both their exact spec files and exact resolved task-context text keyed by canonical task:// URI. Capture any dependency reports selected by task-load from existing managed assignment/report owners, retaining exact assignment/step association. context is a canonically task-URI-sorted array of closed `{uri, task_id, spec, text, reports}` records. uri is exactly task:// plus task_id; spec/text are closed `{filename, bytes, sha256}` records, filenames exactly context/<task_id>/spec.md and context/<task_id>/bundle.txt. reports is sorted by assignment_id then numeric step number; each closed `{assignment_id, number, file}` record identifies the existing managed report, file is the same content-reference shape, with filename exactly context/<task_id>/reports/<assignment_id>/<number>.r.md. Canonical task/assignment/scope validators apply before forming these paths. File counts/sizes/digests derive from exact captured UTF-8 bytes. Duplicate URI/file/report identity, missing dependency or unresolvable context refuses. Cyclic dependencies refuse with the cycle rather than recurse indefinitely. This snapshot is the reviewed instructional context, not a snapshot of the repository code being changed. Live target code and explicit task lifecycle writes remain normal work.

Protected task-load and task:// resolution receive this selected context through the adapter capability. They return the captured text/spec/report inputs, never reread current task specs, bundle presets or dependency reports to supply new instructions. Changed live task/dependency files after acceptance cannot alter consumed context. Explicit lifecycle writes (e.g. marking the selected task done) still use the maintained task owner and do not replace the snapshot. Step instruction text/source targets are already materialized; protected driving must use the captured materialization rather than resolve a workflow/skill again from current source. An uncaptured task URI/report/instruction source refuses before consumption. Ordinary local resolution is unchanged.

### Bounded artifact, definition and canonical storage

Inline job plus step content is not the contract: the measured default qjx graph exceeds the 32KiB definition ceiling. The source preparation owner builds one complete Git bundle containing a closed prepared-input tree: `manifest.json`, `definition.json`, `job.yaml`, `steps/<exact filename>`, and the manifest-declared task/context/report files under `context/`. Only regular 100644 files, canonical relative paths and that exact inventory are allowed; reject symlinks, submodules, executable modes, extra files or prerequisites outside the bundle. This is transport input to the existing authority, not a second work ledger or a new candidate/result acceptance.

The registered definition gains one closed `prepared_work` object with exactly `version`, `task_id`, `scope`, `prepared_head`, `prepared_tree`, `manifest_bytes`, `manifest_sha256`, `selection_sha256`. Version is Integer 1; Git head/tree are exact 40-hex IDs. The manifest has exactly `version`, `assignment_id`, `project_id`, `task_id`, `scope`, `job`, `steps`, `context`, with fixed top-level order. `job` is `{filename, bytes, sha256}` with filename job.yaml; steps/context record the exact file/content identities above. `selection_sha256` hashes compact UTF-8 JSON of the manifest in this order; maps inside it use recursively sorted string keys and arrays use numeric step order/canonical URI and identity order. The manifest is that canonical JSON plus one newline; `manifest_sha256` hashes its exact bytes. Full content digests hash bytes, never parsed/reformatted content. To avoid a circular Git identity, definition.json contains the managed definition fields without prepared_work; the authority derives the final prepared_work reference from the verified graph and checks the launcher's retained final definition bytes/digest against this derivation. No trust flags, arbitrary paths or caller-selected storage roots.

qk0.3 extends the existing register_assignment producer/consumer operation to accept this transfer through Server/Client/TransferCodec's existing one-part candidate framing and CandidateTransfer quarantine/object verification. It does not invoke submit_candidate, require an attempt before registration, create a new upload ledger, or change candidate/result semantics. The small closed registration header contains mapping_id, assignment_id, definition_digest, prepared_head, prepared_tree, manifest_sha256, expected_generation and transfer; the request's ordinary operation/mutation identity remains unchanged. The authority extracts definition.json/manifest/files from verified objects, validates preparation association and final definition digest, then commits the final definition and the exact submitted verified bundle as blobs in the SAME existing registration JournalMutation. It stores the received authenticated bytes, not CandidateTransfer's reexported bytes; reexport metadata is not substituted for the retained request digest. A received bundle alone creates no registration, reservation or execution permission. A replay uses the original accepted registration/blob; different bytes/digest under the same mutation refuses.

Keep existing limits: final definition 32,768 bytes; registration transfer control header 16,384 bytes; TransferCodec candidate body and CandidateTransfer expanded content each at most 64MiB; original release JSON at most 65,536 bytes; transfer concurrency/deadlines remain the existing Server/TransferCodec rules. The manifest and definition are each at most 32,768 bytes within the artifact; count at most 4096 files including context, at most 256 selected steps and at most 256 task-context URIs. Each text file is at most 1MiB and aggregate expanded bytes at most 64MiB. Reject every bound before accepting registration or creating a worker. The default leaf graph must fit these unchanged bounds. No frame/definition cap increase.

The registration result records source-derived prepared_bundle_ref, prepared_bundle_bytes and prepared_bundle_sha256 alongside definition_ref/digest/generation. The registry/inventory producer and read-only consumer expose these three fields and selection_sha256 from that exact retained registration; registration-only rows expose them too. qk0.0's existing inventory pagination/commit binding remains unchanged, and qk0.1 recovery compares these fields without downloading/rebuilding graph content. These are blob references in the existing EvidenceJournal, not local source_config paths. Canonical registration and exact expected generation select the immutable artifact. Definition source_config remains provenance metadata; it is never a worker-readable path selector. The captured managed task/project IDs and parsed preset fork-root structure must agree before registration; the source handler derives the reviewed-status/root association from artifact task specs and generated initial step structure, never a supplied reviewed=true flag. Reservation requires scope and task/project associations equal prepared_work. Any generation/definition/selection change refuses; never rebuild from current assignment files. Replacement definitions remain subject to existing active-attempt conflict rules.
