# Protected physical prune source candidate

Draft for independent review, 2026-10-07. No public capability or task promotion is delivered by this document. This preserves qk0.2's actual workspace-removal outcome, separately from slice retirement and disposable display/cache cleanup.

## Existing source boundaries

`ProtectedServiceReceiver#execute` already admits a distinct active request through request_service, export_candidate, begin_dispatch and fresh service_authorization, executes a fixed installed operation, then imports its evidence through complete_service. The target's sealed attempt cannot request this effect: a separate provisioned maintenance assignment/attempt supplies the request and candidate/review. Its executable, staging and evidence sink must survive outside every deletion target. A host-maintenance service operation may have only its provisioned executor and fixed argv; an arbitrary path, shell or submitted caller identity never selects privilege.

`LaunchLifecycle#with_execution_slots` is source-only, holds sorted protected slot locks and its mutex, selects exact original/candidate history and canonical snapshots, and wraps complete retained Inbox inventory. Every root must pass slot_reusable! before any removal. maintenance_boot_baselines! exports original evidence only while those same contexts remain held. retire_released_parent! stops the execution parent; it removes no workspace. None of these methods is presently a public workspace-cleanup route.

Local `PruneOrchestrator` supplies executed Git preservation checks, fresh HEAD/branch comparison and local removal, not protected authority. `LifecycleExclusion.default_root` currently ignores its repo_root argument, uses ambient CACHE_BASE/project discovery and unbounded Git capture; removed? treats malformed JSON/type as absent. It cannot be adopted as the protected exclusion owner unchanged. A corrupt removal marker cannot authorize a start; an explicit installed state root/key shared by every supported creator must replace ambient selection for this composition. Legitimate absent state differs from corrupt/unreadable state. Existing local consumers need a separately tested correctness repair before sharing this owner; no cache lock is a kernel/terminal/release proof.

## Proposed closed target and live operation

The user selects protected project, mapping, assignment and attempt, plus the immutable original descriptor SHA, original scope-binding event and reservation-release event; preview also records selected canonical revision, exact Git HEAD/branch and verified preservation destination refs. These are selectors/revalidation inputs, never a caller path or permission. The source resolves the workspace exclusively from the selected original protected mapping and its canonical assignment. Unsupported target layout refuses. A changed object at a resolved path must survive.

Dry-run is read-only and reports separately terminal/release authentication, preservation, current/candidate reference conflicts and removal eligibility. Apply uses a stable caller-visible service mutation/request identity and exact preview binding; the usual fresh service admission and proposal policy still apply. No target attempt is reopened. Current/candidate selected roots, canonical repository/checkout, descriptor/history/public-key storage, imported evidence, boot/network artifacts, maintenance requester executable/staging and evidence sink are excluded from deletion. A root cannot become eligible merely because a descriptor lookup fails.

The fixed operation runs the existing maintenance owner in-process with its installed authority principal/roots and exact protected original/candidate transaction. It does not issue a second RPC to acquire maintenance while holding its locks. Complete eligibility and actual current closure remain required; terminal metadata is no live grant. No removal is possible until a independently reviewed successor descriptor no longer references the target; descriptor publication and cleanup sequencing must be explicitly joined by the provisioning owner, rather than treating an unpublished candidate as permission to destroy a current root.

Within held maintenance contexts, the operation acquires maintained physical workspace lifecycle exclusion using the same explicit source-owned root/identity as supported provisioning. Order is existing slot locks → retained inventory locks → workspace lifecycle lock; no creator may invert this order by holding workspace exclusion and requesting a slot RPC. Creator paths that cannot follow this order must refuse this protected composition until migrated. Same-owner preservation inspection and exact captured Git/filesystem identity revalidation occur inside that exclusion. No service/status/complete RPC or native wait takes these locks recursively.

After preserving exact commits and required dirty/untracked/ignored artifacts to authenticated surviving destinations, the remover records the maintained removal fence before atomically capturing the exact target object for deletion. Failed capture/revalidation preserves any replacement. The operation stages a structured receipt outside the target containing selected original/candidate descriptors, canonical prefix and binding/release selectors, affected-root eligibility evidence, exact preserved refs/artifact digests, original/captured filesystem identities and removal outcome. It exits all maintenance/lifecycle locks before the existing receiver sends complete_service. A request timeout or lost reply yields canonical uncertainty; no blind deletion retry.

Recovery uses existing service_status and claim_service_settlement/inspection producers. A fixed operation-specific inspector must compare retained request/receipt identity, preservation destinations, original target and any captured object; absence alone is not success/no-effect. A removed marker alone is not a service completion receipt. Known preserved-and-removed evidence may complete the original request; positively untouched original may support no-effect; mismatched or partial evidence remains uncertain. No new journal, controller or automatic target recreation.

## Complete proposed composition for review

The fixed operation name is `prune-preserved-workspace`, installed through the existing ServicePolicy local host-maintenance operation with its exact protected executable and provisioned executor. It runs the same trusted Lab installation owner; there is no separately delivered DeploymentMaintenance class in the inspected source. `LabHerdrNative::Installer` currently owns installation lock, inhibition, protected original/candidate/history verification, all-root eligibility and candidate publication. This child adds a cleanup phase to that owner, not a parallel deployment publisher/root broker. Installed executable and evidence sink remain outside the selected obsolete workspace. Executor credentials are installed facts, never requested UID/root mode.

Existing ProtectedServiceHandler has a 30-second whole-child deadline. This child must make the installed fixed prune operation use a bounded 300-second deadline in that same handler, with bounded 16KiB/8KiB stdout/stderr and group cleanup preserved; ordinary operations retain 30 seconds. The client waits only its existing bounded service/status exchanges, not the entire removal. Deadline/child death after dispatch leaves the accepted request uncertain and invokes the fixed inspector, never a fabricated no-effect. Actual controlled owner timings must distinguish setup, permission exchanges, preservation and deletion and demonstrate the selected bound; this is an explicit required handler change, not a claim the current 30-second operation already supports arbitrary maintenance history.

A provisioned maintenance mapping uses a separate project/authority and fixed workspace. Its exact descriptor entries, authority service and credentials are unchanged across the target publication transaction. It is neither an affected mapping nor an inhibited target unit. Its active reviewed attempt supplies service request, candidate and authorization; target inventory includes only affected original/candidate roots. If descriptor/project changes make the requester affected, preflight refuses the transaction instead of granting a bypass for active maintenance. The target may belong to another project; the operation's fixed policy explicitly selects that project/authority pair, while service permission still belongs to the maintenance project. No ordinary target worker obtains this privilege.

Publication is a prerequisite, not an effect of prune: the provisioning owner first completes its existing installer transaction. It retains the old immutable descriptor/history/key/evidence, publishes the exact selected successor descriptor, refreshes proofs and publishes the immutable installation document selecting that successor. Prune previews `deployment_refresh_required` until this is positively verified. The successor must omit the obsolete physical workspace from every mapping; the original mapping remains available only through retained literal history. Both published current descriptor content identity and history.candidate must equal that completed successor. A newer descriptor, missing installation document or still-selected alias blocks apply. The child does not remove a root to make installation complete.

For apply, the fixed operation enters the installer's existing lock first, selects the same completed original/candidate transaction, and installs/validates its source-owned inhibition for affected target admission units only. It reuses the maintained stop/drain and all-root `with_execution_slots` eligibility owner. It does not inhibit the unchanged maintenance authority. Lock order is installer publication lock → exact sorted slot locks → retained inventory → explicit shared-creator workspace exclusion. Each current descriptor/installation/ref identity is rechecked before filesystem mutation. No RPC occurs inside these exclusions. Original terminal/release/proof authentication is supplied by the actual maintenance owner; caller event selectors must equal that authenticated selection.

The input document is closed `{schema, maintenance, target, publication, preservation}`. `schema` is `ace.protected-workspace-prune/v1`; maintenance names exact project/mapping/assignment/attempt; target names exact original project/mapping/assignment/attempt, descriptor SHA, binding/release event digests and canonical commit; publication names exact successor descriptor SHA and immutable installation-document reference; preservation names exact HEAD, branch-or-null and destination refs/artifact references. Paths are resolved solely from installed original mapping and canonical assignment. Request input_digest and target identity bind all these fields through existing service authorization. Preview returns this exact document and its digest; apply cannot substitute current input under the same service mutation.

The actual preservation owner must prove commit reachability in surviving refs and preserve dirty/untracked/required ignored bytes into a surviving authenticated artifact outside the target, or refuse. The physical remover reuses existing Git worktree removal and branch compare-and-delete semantics, retaining common Git object/ref storage. It must reject protected evidence paths and any current/candidate alias before capture. The explicit workspace fence root lives in installed authority state outside the target, resolves by full project/mapping/assignment plus physical object identity, and is joined by every supported worktree provisioning/start path. This child repairs the existing LifecycleExclusion supplied-root and corrupt-state behavior and migrates its protected callers; no separate cleanup state owner is added. Ordinary local prune keeps its own behavior and never supplies protected authority.

The receipt artifact is closed `{schema, request_id, input_digest, maintenance, target, publication, canonical_snapshots, preservation, removal}` with schema `ace.protected-workspace-prune-receipt/v1`. canonical_snapshots is the exhaustive selected mapping/commit/binding/release/proof identity set returned by the authenticated maintenance operation. preservation contains exact executed destination ref identities and imported artifact references. removal contains original object identity, captured object identity or null, outcome (`removed` or `untouched`) and removal-fence identity. The ordinary service receipt binds request/input/candidate and imports this artifact through complete_service after every maintenance lock exits. These fields are evidence, never a second live grant.

The fixed operation-specific no-effect/recovery inspector consumes the existing exact service settlement challenge and request binding. It selects the immutable operation receipt artifacts from the surviving sink, verifies full preservation/publication and target identities, and reports existing supported settlement outcomes. Verified completed removal can become original succeeded service evidence; positively unchanged target with no captured object/issued removal can support no-effect. Partial capture/removal or missing/corrupt evidence remains uncertain with explicit reconciliation action. It never infers outcome merely from a pathname missing or a removal marker. A retry of an accepted request returns existing canonical status; it never reexecutes removal. Same original surviving handler may finish its one accepted invocation, but no new birth adopts effects by absence.

Only after verified removal and canonical outcome is admission inhibition released by the same installation owner, after checking completed successor publication again. Failure retains inhibition/recovery evidence without changing unrelated scope permissions. This source outcome and recovery inspector are mandatory qk0.2 delivery; installed enforcement remains separately gad.2. All decisions above are proposed for exact independent review before implementation, rather than unresolved defaults delegated to the implementer.

## Selected B: exact original Installer capability
