# Scoped publication source contract candidate

Source base `818a4f64f`. Draft for independent review; no task promotion or publication authorization. The vs3 behavioral spec remains normative. This document resolves source composition, not installed gad.2 acceptance. Implementation must not start until the continuation and executor-HITL joins below are reviewed.

## Existing owners and concrete gaps

- `.ace-bin/ace-rubygems-publish` owns queue discovery, artifact preparation, dependency waves and push. Its `push_one` currently returns published/already_published/otp_rejected/failed; live entry requires OTP before any push. Reuse this owner, extracting a callable publisher result boundary; do not write a second publisher.
- `ProtectedServiceReceiver#execute` owns original claim, materialized candidate, begin_dispatch, fresh ServicePolicy admission and complete_service import. Duplicate claims do not invoke the handler again. `ProtectedServiceHandler#execute` owns a bounded 30-second subprocess and only terminal succeeded/failed responses. Neither currently supports pausing for OTP and explicitly continuing a known no-effect publication phase.
- HITL `Lifecycle::Client#create/consume`, Store and OtpVault own authenticated requester-only ephemeral OTP. Store requires operation/result_ref/input_digest/expiry and an active managed requester's attempt. `Providers::Lab::AssignmentBinding` currently uses local AttemptCoordinator; it cannot attribute a distinct service executor to the original worker's attempt. No installed publisher credential grants this ownership.
- EvidenceJournal/ServiceEvidence own canonical service outcome/import. An OTP-required classification is not failed completion, effect absence for another push, or permission to repeat an uncertain request.

## Exact retained publication input and admission

One request publishes ONE explicitly named artifact, rather than an ambient pending queue. Existing scoped service operation is `publish`, admitted by the existing installed ServicePolicy operation and direct/standing/resolved-proposal authorization. No new authorization dialect or privilege is introduced.

Structured input is closed `{target, publication}`; target is `{resource, artifact_digest}` with resource `rubygems:<gem-name>:<version>` and mandatory SHA256 artifact digest. Publication is exactly `{gem_name,version,head,registry,artifact_relative_path}`. Registry is fixed `https://rubygems.org`; no caller URL or credential target. Head equals the canonical candidate head (exact40 SHA current owner). Gem name/version match the held gem's package metadata. Artifact path is a bounded safe relative regular-file path within the authenticated materialized candidate, not an executable or an external path. The exact prepared `.gem` must be retained in that candidate; build cannot silently replace it after authorization. Existing ServiceInput64KiB/strict JSON depth16 bounds apply, with duplicate keys/non-finite values rejected by the publication validator.

Receiver/kernel/claim/current-generation/policy and accepted review checks remain unchanged. Extracted publisher validates the joined request/input/execution envelope, holds and hashes the exact artifact before provider work, and rechecks its metadata/path identity before each permitted push. A complete queue release is several independently scoped artifact requests; no first artifact authorizes siblings.

## Publisher classification and secret boundary

The fixed publication entry receives the same closed receiver envelope on stdin. No caller argv, command, environment mapping, OTP, credential or alternate handler is accepted in service input. Selected executor uses its provisioned registry credentials; workers and coordinator never receive them.

First attempt invokes the existing push boundary without OTP. Success is accepted only after exact registry name/version/artifact digest verification. Already-present exact bytes may be adopted read-only; a conflicting digest refuses. A positive provider OTP-required/rejected/expired response must prove that this attempted push was rejected before acceptance; response loss, unclassified error or ambiguous registry state is uncertain, never eligible continuation.

Result classifications are `succeeded`, `otp-required`, `otp-rejected`, `otp-expired`, `failed`, `uncertain`. Classification uses bounded provider output transiently; persisted evidence is a closed value-free code plus exact request/input/artifact/registry selectors and sanitized result references. Non-OTP failure never asks for OTP. Uncertain never asks for OTP as a way to retry. Existing raw script output must not escape the classified entry. No secret appears in argv, stdout/stderr, canonical blobs, task files, reports or durable events.

OTP create/consume belongs to the exact authenticated original service executor. Original worker assignment/attempt/project are routing correlation, never executor impersonation. The behavioral spec requires exact requesting executor (line38) and correlated assignment/attempt/project ask (line44), not an executor-owned native attempt. The earlier candidate's additional executor native-attempt prerequisite is superseded. Deployment's distinct receiver UID invariant remains unchanged.

Add a fixed `ServicePublicationBinding` implementation of existing HITL Lifecycle::Binding, composed inside the protected HITL boundary with the SAME installed LaunchLifecycle/Endcap service owners. It is selected only by a closed publication binding attached to OTP create, not by a caller class/name or alternate validator. Existing ordinary AssignmentBinding is unchanged. The binding uses the original worker assignment exclusion through LaunchLifecycle.with_assignment, authenticates original canonical service record/dispatch/challenge and current executor kernel credentials/birth, and HOLDS that exclusion across the Store create/deliver/consume transition. Do not implement this as a remote read followed by an unlocked Store write. The fixed installed composition must give the HITL boundary the actual authority owner; no client-provided coordinator, copied journal, new service grant or synthetic native session. Service requests route to the coordinator's existing completion/HITL channel; reverse delivery never claims a native pane owned by the receiver. Missing installed same-owner composition refuses before creation.

The closed create binding is `{schema,mapping_id,assignment_id,attempt_id,request_id,claim_binding,input_digest,candidate_generation,head,challenge_digest}` with schema `ace.hitl-publication-binding/v1`. The existing create project/assignment/attempt/input_digest/operation/result_ref must equal this binding and canonical challenge; operation is publish and result_ref is the retained challenge reference. Requester is always kernel-derived executor account, not a field in this object. Store retains these non-secret selectors in its existing request record. Consume accepts only the existing request ID; it reloads this binding, rechecks current challenge and original executor birth under the held owner scope, then transfers one answer to that exact authenticated requester. Answer delivery never grants publication authority. Terminal, changed birth/input/candidate/claim/challenge or unavailable policy cancels/refuses using existing lifecycle classifications. This is an explicit source amendment to the worker-attempt-specific current Lab binding, not a claim that its existing native reverse validator supports service executors.

Challenge result_ref identifies the canonical retained non-secret OTP-need evidence for this original service request; input_digest is the exact accepted publication input. Operation is `publish`. Only six ASCII digits from authenticated HITL consume enter the publisher-owned memory and its immediate child environment as GEM_HOST_OTP_CODE; never shell/argv. Clear temporary buffers and remove child OTP environment on return/exception. A consumed replay returns no secret and cannot authorize another push.

## Required same-journal continuation precision

No 30-second handler is held while waiting for a human. Retain OTP-need evidence and phase in the SAME canonical service request/import owner, then return a non-secret pending status. Generic terminal completion/import and immutable completion_digest conflict rules must remain unchanged. This requires a reviewed publication-only extension; the current generic terminal protocol does not already deliver it.

Proposed fixed authority methods on the existing EndcapServices/Router/Server boundary are `publication_challenge` (executor uploads bounded classified no-effect OTP-need artifact) and `publication_continue` (same authenticated original executor, exact challenge digest, original claim/input/candidate/policy and expected authority generation). They use existing service input/evidence transfer purposes and same canonical request record/CAS, not a second journal, broker or secret RPC. Closed schemas and role grants must be added together; these names are a review proposal, not delivered APIs.

Challenge CAS accepts only the original dispatch's authenticated positive rejected-before-acceptance evidence with no terminal completion_digest. It retains a unique challenge generation/digest and becomes OTP-pending. Continue revalidates original executor birth, current permission and exact input/artifact/candidate, then atomically consumes that exact challenge once and records a new issuing phase BEFORE effect. OTP bytes and HITL answers never enter these messages. The receiver's source-owned continuation uses the exact held original artifact and publisher entry, not fresh queue discovery. A duplicate continuation is status-only. Any lost reply after issuance stays uncertain; no automatic continuation, new challenge or effect retry. Only positively classified fresh OTP rejection can yield a new challenge; it never clears an older uncertain issuance.

Recovery after process/service restart reads canonical status and registry evidence for the exact original tuple. Exact existing artifact success may complete/import once; unknown or conflicting registry bytes stay uncertain. Recovery cannot reuse a consumed OTP, re-push, infer success from version existence alone, or treat no local process as effect absence. Terminal complete_service keeps its existing immutable digest/CAS and one completion/import receipt.

This API addition and the protected executor-HITL binding are the two actual readiness decisions. Independent review must approve their exact closed fields/producer-consumer ownership before implementation; do not hide them behind generic callbacks. If a smaller existing owner can express them faithfully, replace this proposal before coding rather than add parallel paths.

## Receipt, workflow and acceptance

Canonical succeeded receipt/import binds original project/assignment/attempt/request/claim/input/candidate plus artifact name/version/digest/head, fixed registry, accepted authorization and verified publisher outcome. Failed, OTP-pending and uncertain remain distinct. Merge receipt is never publication evidence. Workflow returns exact receipt/status or a routed blocker, not prose success, and keeps coordinator responsive while the executor owns work.

Source matrix: direct success; exact already-present readback; needed OTP; rejected/expired fresh OTP; non-OTP failure without ask; lost push reply; conflicting registry digest; duplicate challenge/continue/completion; foreign executor/birth; stale candidate/input/challenge; terminal original worker attempt, changed executor birth or unavailable service policy; reply loss after consume; cancellation/expiry; canonical CAS interruption. Every row observes provider invocation count, exact canonical record/import, HITL challenge attribution and no secret in outputs/files/events. Fake registry/publisher/clock and OS identities are controlled; actual Client/Server/CAS/HITL IPC owners run. No real push, credentials, Telegram, native/root probe or task closure.

qkb.1 SC4 requires the existing publisher/OTP handoff to route a classified blocker when unavailable; it does not depend on vs3 completion. vs3 depends on qkb.1, so its eventual positive scoped OTP receipt is downstream evidence, not a qkb.1 closure prerequisite. Actual installed distinct-account executor, registry credentials and genuinely authorized release belong solely to gad.2 `scoped-publication` with gad.b provisioning.

## Closed publication continuation proposal (successor precision)

Both operations use the existing mutation frame `{version,operation,mutation_id,params}` and executor role ONLY; mapping/project selection, peer kernel capture, original executor exact birth and current service permission are checked before any upload body and again under the existing assignment/CAS owner. Parameters for publication_challenge are exactly `{mapping_id,assignment_id,attempt_id,candidate_generation,head,request_id,claim_binding,input_digest,expected_generation,receipt_sha256,transfer}`. Parameters for publication_continue are exactly the same selector tuple without receipt_sha256/transfer, plus `{challenge_digest}`. No OTP, requester identity, registry URL, artifact path, new authorization or process flag is accepted in either request. Existing ID/SHA/head/integer/transfer validators and bounds apply. Challenge uploads existing receipt_artifacts framing; continue is bodyless.

Challenge artifact is closed `{schema,classification,request_id,input_digest,claim_binding,candidate_generation,head,registry,gem_name,version,artifact_digest,dispatch_event_digest,previous_challenge_digest}`. Schema is `ace.publication-otp-need/v1`; classification is exactly otp-required/otp-rejected/otp-expired. Previous challenge is null for the original dispatch, otherwise the exact last consumed issuance's challenge digest. The authority reconstructs publication input from retained target/publication, normalizes with the shared validator and verifies its digest; every artifact selector must match it and original dispatch. No arbitrary artifact reference can substitute that admitted candidate. Challenge acceptance requires a positively rejected-before-acceptance publisher classification, not process absence, timeout or ambiguous output. No existing terminal completion_digest may be overwritten.

CAS appends publication-specific phases to the SAME service record: original dispatch_started → otp_pending with one challenge_digest; otp_pending → issuing through continue, recording consumed challenge_digest and exact original executor before effect; positively classified fresh rejection may append a new otp_pending challenge. An issuing phase with unknown outcome remains uncertain and cannot transition to a new challenge or repeat issuing. expected_generation is exact current authority generation before CAS; it is never inferred from candidate generation. Duplicate mutation replays only the identical canonical record; duplicate challenge/continue with a different mutation cannot create another challenge/effect. A stale generation/digest/tuple refuses. Continue returns the source-owned issuing event digest and current generation, never a permission boolean; fixed receiver verifies those exact values and original retained input/artifact before one push. Reply loss leaves uncertain, with no resend.

Success uses existing complete_service receipt/import, extended publication result validation only; pending/issuing are not terminal completion receipts. Immutable completion conflict protections remain. Status projects original selectors, phase, challenge/issuing digest and generation value-free; it never exposes OTP or turns accepted claim into success. Recovery is read-only exact registry evidence and canonical status; no continuation is manufactured on restart.

Root's review of21d507 withheld readiness for unspecified schemas and executor provisioning. This successor removes the unsupported native-executor premise and specifies same-authority service-bound HITL attribution plus closed continuation selectors. It remains draft pending independent review of the installed same-owner HITL composition and publication phase rules; no code, promotion or real publication.

## Installed process composition and atomic HITL transition

Use the existing `Lifecycle::Service(root:,binding:,policy:,socket_path:)` constructor and its per-peer `store_for`/in-memory OtpVault. SAME protected authority startup constructs the publication HITL service as a sibling listener in the SAME process as its LaunchLifecycle/Endcap instance. This is a source-owned composition extension, not an external broker RPC pretending to hold a lock. Existing installed publisher endpoint selects this service's protected socket and expected authority UID; the existing HITL client endpoint/peer checks remain mandatory. Installer must provision the existing HITL store/socket access for that authority and the declared executor; registry credentials remain executor-private. Ordinary agent HITL service and AssignmentBinding are not replaced.

The installed constructor supplies a fixed binding router with only two source-defined cases: ordinary AssignmentBinding when no publication binding is present, and ServicePublicationBinding only for kind=otp, operation=publish and an authenticated installed service executor. An executor cannot use the ordinary case with original worker selectors; it refuses. A worker cannot select the service case. Request fields choose correlation only; service branch admission is established by kernel peer UID/GID/groups, fresh kernel PID/start/boot identity, original recorded service executor and canonical challenge. ServicePublicationBinding receives the full authenticated Peer (not username alone), and passes it to the same Endcap admission owner; payload-supplied peer/birth is forbidden. The create binding is persisted only after this validation, and subsequent reads reselect from the retained closed record, never a fresh caller binding.

For publication-only Store transitions the order is existing HITL request lock → original authority slot/assignment exclusion (the maintained LaunchLifecycle.with_assignment order, no recursive acquisition) → canonical record/challenge/current permission validation → bounded Store publication/answer consume commit → release authority exclusion → release HITL request lock. No Endcap mutation path calls the HITL Store while holding authority locks; continuation runs only after HITL consume returns and its locks are released. Create must validate AND persist within this same held scope: current prepare_request validation followed by separately unlocked persist_request is insufficient for this service binding. Deliver/consume similarly hold the binding around their existing locked terminal transition; consume waiting/polling occurs outside authority exclusion. Only bounded local filesystem/vault work is allowed while held, no human wait, network/provider invocation or listener round-trip.

Create retains exact original executor PROCESS_FIELDS captured from authenticated peer and verified equal to canonical dispatch executor. Consume demands that same birth, not merely same UID or a descendant; executor restart cannot consume an old secret. Human answer delivery is separately authenticated by existing HITL access policy and does not become executor. Expired/rejected challenges are explicit no-secret classifications; service/broker restart loses ephemeral vault bytes, so pending challenge status remains but cannot fabricate consumed answer or fresh push. A new ask requires a newly canonical positively rejected-before-acceptance challenge. Lost create response resolves by exact request ID/status without creating another request; lost consume response cannot retrieve the consumed secret again or proceed to push. The requester reports uncertain/blocker. Later authority continuation is still necessary and may refuse if generation/policy/candidate changed after consume; disposal of a now-unused OTP is safe and never renews authority.

This installed same-process constructor/Store binding extension is a required delivered source owner, not existing production behavior. Source tests must run actual authority+HITL listeners in the same process with real canonical Git and Store, controlled kernel identities and fake publisher; prove held transition prevents concurrent terminal/CAS, foreign birth cannot receive secret, ordinary branch cannot bypass service validation, and no lock inversion/provider work under exclusion. Installed DAC/process provisioning remains gad.b/gad.2 acceptance. No synthetic executor assignment/native session or role-UID relaxation is needed.

## Bounded HITL transport and ask disposition — readiness correction

Existing Client#request opens and writes its socket before computing its read deadline, and its default transport allowance is ten seconds; a positive consume timeout alone cannot enforce the original tick deadline. Require a minimal source amendment to this SAME client owner: `Client#request(op, params, deadline:)`, with `read(id, deadline:)`, `consume(id, timeout:, operation:, deadline:)`, `create(..., deadline:)` and `cancel(id, reason:, deadline:)` forwarding one finite absolute monotonic deadline. Endpoint connect, bounded frame write/flush and reply read must all use that original deadline; read waits use the earlier of it and the existing operation deadline. No renewed deadline, Timeout.timeout around a blocking cleanup, parallel client, or new wire operation. Nonblocking connect/write/read must preserve existing endpoint/peer authentication and frame limits. This is an explicit proposed source/API amendment, not an implemented capability. Each tick passes its deadline and schedules at most one finite wait; status/read/cancel/create work that lacks remaining budget continues in later ticks. A client transport deadline cannot prove that the server did not consume an OTP: the receiver discards unavailable secret bytes, performs no continuation/push, and resolves the same request ID read-only. The finite positive server wait eventually ends even after client disconnect. No socket or assignment exclusion is retained across human wait.

The receiver chooses and retains the existing explicit HITL create `id` BEFORE creation. Unknown create/cancel/consume replies resolve that SAME ID with authenticated read/status, rather than create another ask, repeat secret transfer or interpret absence of a local entry as terminal. Under the SAME held assignment authority across Store creation, ServicePublicationBinding and the existing Store must enforce at most one active request for the exact requester birth/publication request/challenge digest. Existing Store records are the sole durable ask ownership; no second ask ledger or canonical publication phase is introduced. A duplicate ID with identical retained binding is resolved read-only; changed binding conflicts. Never recreate an ID whose existing request or terminal disposition is unconfirmed. A fresh ask ID is permitted only after the predecessor's exact cancelled/consumed terminal record is authenticated and the unchanged canonical phase is still otp_pending, with no issuing event and the same live original receiver/artifact/policy. Lost creation acknowledgement cannot produce two asks.

Local OTP challenge expiry or MemoryVault loss after HITL service restart is classified as `otp-answer-expired` or `otp-answer-unavailable`, respectively, not publisher `otp-expired`, `otp-rejected`, registry rejection or no-effect push evidence. The live original receiver clears any answer bytes, explicitly cancels the exact old pending request through the existing lifecycle owner, and waits for its authenticated terminal/cancel confirmation. A consumed terminal whose answer was lost is also answer-unavailable; no answer is replayed. It then creates one fresh bounded-expiry ask for the SAME already-authenticated canonical no-effect challenge, with the same publication input/claim/artifact and original executor. Recheck original birth, held artifact and canonical phase at this transition; a later issuing/terminal/stale challenge refuses. Each ask has a finite expires_at bounded by the existing OTP TTL, and expiry is checked before consume and again before publication_continue. Re-asking for a lost/expired secret does not append fabricated provider rejection, consume a publication challenge, or invoke a provider. Only an actual positively classified fresh provider OTP rejection may append a new canonical challenge. Unknown cancellation/create state returns a value-free routed blocker and remains same-ID status-only until positively resolved.

A publisher receiver restart is different from a HITL vault restart: the original executor birth and artifact handles are lost, so the replacement cannot consume/create an ask or continue the old challenge. Project `publication-blocked` with reason `original-executor-unavailable` (retain canonical otp_pending or uncertain phase exactly) and route it to the coordinator through its existing completion/HITL channel; never leave an apparently progressing unattended tick. The SAME HITL binding invalidates/cancels the old request on an authenticated lifecycle check of its unavailable recorded executor. Read-only canonical/registry recovery may report exact success or a blocker under existing admission; it cannot manufacture original-executor completion authority. Fresh publication requires separately admitted authorization/claim after the original service request is legitimately retired by its owner, not an automatic replacement ask or push. If the old ask cancellation cannot be confirmed, report `otp-request-unresolved` and preserve its attribution. These are explicit safe blocked outcomes, not provider failures or a claim that missing source retirement/installed recovery already exists.

Required source rows additionally exercise: delayed/no answer returns within the original tick transport budget; connect/write/read backpressure and no budget renewal; local OTP expiry -> confirmed cancel -> exactly one new ask/same canonical challenge/zero push; in-memory vault loss -> confirmed terminal disposition -> exactly one new ask; lost create/cancel/consume acknowledgement -> same-ID resolution/no duplicate ask; expiry between answer transfer and continue -> zero push; receiver restart -> exact routed blocker/no new ask or continuation; late answer to cancelled predecessor refuses; and concurrent ask creation under the same challenge cannot create two active requests. Existing original-worker terminal, exact executor birth and current service-policy negatives remain required; there is no executor-owned managed attempt.
