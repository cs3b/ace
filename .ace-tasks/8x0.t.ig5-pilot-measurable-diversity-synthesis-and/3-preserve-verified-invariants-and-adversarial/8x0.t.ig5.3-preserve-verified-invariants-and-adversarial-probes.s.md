# Preserve verified invariants and adversarial probes

## Behavioral Specification

### User Experience

A later task reuses a verified invariant and minimal adversarial reproduction without rereading dozens of historical reviews.

### Expected Behavior

- Export only confirmed valid findings, retaining original finding/source identity, revision, verified disposition, invariant, minimal reproduction, expected result, applicability and uncertainty. Deduplicate one defect with multiple independent sources.
- Distinguish a general rule from a pg/Vitest/Node-version-specific observation. A suggested improvement or unsupported report cannot become a mandatory invariant.
- Seed the first package with this PostgreSQL experiment: physical completion versus caller rejection; owned-work drain and stop after failure; evidence ACK before producer progress; reset ownership; child/skip boundaries; precise warnings; local-validation recovery; native exit behavior.
- Convert the historical reproductions into portable probes with setup/cleanup and positive/negative controls during implementation. Do not claim the current local hardcoded scripts already form a portable library.
- Planner consumption flags a separate engineering slice when verification has its own cross-process communication, persistence, concurrency ownership or failure recovery. Preserve the parent user-visible outcome; the signal is advisory and justified by boundaries, not guessed LOC.
- A catalog entry remains auditable when superseded; version drift or a failed control makes applicability uncertain and prevents silent reuse as proof.

## Interface Contract

A finding export workflow emits a catalog entry plus probe package; a task planning/synthesis workflow consumes entries by applicability and lists what was included/excluded with reasons. This is a workflow/artifact interface using existing ACE context loading, not a new general-purpose execution service.

All interfaces described here are proposed acceptance contracts, not a claim of currently installed functionality. Draft usage scenarios are in `ux/usage.md` in this task directory.

## Success Criteria

- [ ] SC1: Export one confirmed finding and reject an unverified suggestion; merge duplicate sources without losing attribution.
- [ ] SC2: Run the initial PostgreSQL probe package on known faulty and repaired fixtures: it fails the faulty behavior and passes valid controls with cleanup complete.
- [ ] SC3: Change a required driver/runtime version or remove reproduction evidence; mark applicability unproven rather than asserting success.
- [ ] SC4: Plan a verifier crossing process/persistence/recovery boundaries and show an independently testable slice; do not split a trivial assertion-only verifier.
- [ ] SC5: A fresh task consumes invariant/probe entries without the historical review transcript and can reproduce the documented result.
