# Run isolated discovery candidates from one baseline

## Behavioral Specification

### User Experience

An operator launches three bounded exploratory solutions from one pinned starting state and receives isolated, attributable results even if one worker fails.

### Expected Behavior

- Create three separate candidate attempts/worktrees and fresh contexts from the same fixed SHA, contract and recorded environment. No candidate can write another candidate's files or accepted evidence. One writer owns each candidate.
- Use the R3 discovery profile: implementation, focused verification and at most two completed review rounds; no changelog, retrospective, task completion/archive, release gate, mandatory PR publication or merge-ready claim.
- Candidates cannot consume sibling code, findings or conversation context before discovery closes. Orchestration can observe status and failures without leaking solution content.
- Export each candidate's identity/head/base, actual provider/model binding, rationale, executed test/probe evidence, verified findings, invariants and known uncertainty. Model attribution is withheld from the later judgment view, not discarded from audit provenance.
- Failed, stopped and incomplete candidates remain visible. Duplicate dispatch/restart must reuse or reject the active owner, not spawn a second writer. Reuse existing assignment attempt semantics rather than a separate Lab execution engine.
- Emit stage/event hooks and artifact references needed for L5 accounting from the start, including failed attempts; the benchmark task supplies analysis rather than reconstructing missing history.

## Interface Contract

A discover-only assignment recipe accepts task contract, fixed base, three resolved candidate-role bindings and the discovery profile. Status lists each attempt and its terminal state; its candidate manifest is the input to L2. This recipe ends at artifact handoff. It does not call normal full-delivery completion steps.

All interfaces described here are proposed acceptance contracts, not a claim of currently installed functionality. Draft usage scenarios are in `ux/usage.md` in this task directory.

## Success Criteria

- [ ] SC1: Run three isolated fixture candidates from identical base and environment; each result identifies its own head, tests and uncertainty.
- [ ] SC2: Fail or stop one worker while the others finish; preserve all three outcomes and prove no cross-candidate file/evidence contamination.
- [ ] SC3: Restart and duplicate-dispatch during active work; retain one owner per candidate and do not rerun completed effects.
- [ ] SC4: Attempt sibling-artifact access and final-delivery promotion before handoff; isolation/policy boundaries deny them.
- [ ] SC5: Prove the discovery command path does not invoke changelog, retro, task closeout or release-check steps.
