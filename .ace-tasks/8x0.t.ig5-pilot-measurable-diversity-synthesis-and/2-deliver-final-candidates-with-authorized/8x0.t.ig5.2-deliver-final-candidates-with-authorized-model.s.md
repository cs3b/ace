# Deliver final candidates with authorized model escalation

## Behavioral Specification

### User Experience

An operator delivers one synthesized implementation with explicit provider bindings, independent review and authorized escalation, while exploratory outputs remain non-deliverable.

### Expected Behavior

- Default pilot roles are GLM Flash, Gemini Flash and DeepSeek Flash discovery; Sol synthesis; fresh GLM Flash final implementation; independent Sol review. Resolve each role to an executable exact provider/model/reasoning configuration before work begins and record it.
- Treat Flash/Sol/Astra as configured roles, not guaranteed product IDs or provider availability. If a required family is unavailable, report blocked setup; do not silently substitute another instance of the same family or send private source to an unauthorized provider.
- The final implementation begins in a fresh context from the common base plus L2 package. Only it enters full delivery, including scoped docs/changelog/task lifecycle, required tests, independent current-head review and explicit merge gate.
- Separate implementer and reviewer execution identities/contexts through the existing authority boundary. Using a different role label alone does not establish independence.
- Astra escalation is optional and only for an unresolved architecture conflict, failing invariants or exhausted campaign. Record the trigger, authorization, exact binding, input and outcome; include its work in total cost.
- No inherited approval for a different operation: authorized escalation does not authorize merge/deploy. No authorization means a visible blocked action, with completed preparation preserved.
- Consume qjl attempts and qkb provider-neutral delivery; do not recreate provider-specific PR logic or a second receipt engine.

## Interface Contract

The pilot assignment declares role bindings, synthesis package, delivery policy and applicable scoped authorizations. Status exposes actual bindings, independent reviewer identity, stage, escalation reason and outcome receipts. A discover-only result cannot be supplied as a delivery-success receipt. Normal merge authorization remains a separate action.

All interfaces described here are proposed acceptance contracts, not a claim of currently installed functionality. Draft usage scenarios are in `ux/usage.md` in this task directory.

## Success Criteria

- [ ] SC1: Execute the default route with test providers then available real configured bindings; record the actual model for every role, with a fresh final implementer and independent reviewer.
- [ ] SC2: Reject unavailable-family silent fallback, same-author self-review and an exploratory receipt offered to the merge gate.
- [ ] SC3: Exercise each escalation reason with and without authorization; authorized work is accounted for, unauthorized work is not launched.
- [ ] SC4: Change the final head after review; enforce current evidence without erasing campaign history.
- [ ] SC5: Complete one final delivery using existing qkb/qjl contracts; preparation is not deployment and merge requires its own valid authorization.
