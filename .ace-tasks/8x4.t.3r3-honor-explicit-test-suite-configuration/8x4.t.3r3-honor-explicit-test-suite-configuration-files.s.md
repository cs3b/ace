# Honor explicit test suite configuration files

## Objective

Let operators restrict suite execution with the advertised `--config FILE` option. An explicit file must never silently select the default suite, especially when an isolated gate requests one package but the default includes the whole repository.

## Behavioral specification

An invocation without `--config` retains the existing ACE default suite configuration resolution and policy. Supplying `--config FILE` or `-c FILE` loads that exact file as the suite configuration, without merging packages from any other suite. Relative file paths resolve from the invoking working directory; absolute paths identify the same file directly. Existing package-path resolution remains unchanged.

The explicit file must be readable YAML with the supported suite configuration structure. Missing, unreadable, malformed, or structurally invalid explicit files produce an actionable diagnostic identifying the requested path and exit nonzero before starting any package. No fallback to the default suite is permitted. Configuration failure does not publish a successful suite result.

CLI overrides for parallelism, timeout, group, target, display and verbosity retain their existing precedence and behavior, applied to the selected configuration. Group selection operates only on its packages. This task does not change default package membership, execution deadlines, hermetic environment policy, test targets, or execution-verdict semantics.

## Interface contract

```bash
bin/ace-test-suite --config .ace-local/verification/assign-only.yml --parallel 1
bin/ace-test-suite -c /absolute/path/assign-only.yml --target feat
bin/ace-test-suite
```

The first two commands execute only packages selected by the explicit suite. The last command uses the current default resolution. A missing explicit path reports that path and exits nonzero, starting zero workers. There is no compatibility fallback or alternate configuration dialect.

## Success criteria

- [ ] Both flag spellings select the explicit file, including relative and absolute paths.
- [ ] A default suite containing package A and an explicit suite containing package B execute only B with the flag; no-flag execution retains A and current default policy.
- [ ] Explicit-file package selection remains authoritative when a valid default suite exists or no default suite exists.
- [ ] Missing, unreadable, malformed YAML and invalid suite structure each fail before any package starts and never report success.
- [ ] Existing CLI precedence and group selection apply to the selected file; no unrelated default packages enter the run.
- [ ] Public usage describes the authoritative explicit-file behavior and errors.

## Vertical slice

One standalone, small slice: operators select a suite file and receive execution or a clear configuration failure. No dependency on the Lab readiness or qjz implementation lanes.

## Verification plan

Component checks cover selection, parsing and diagnostics. Maintained real-CLI tests use isolated temporary projects and tiny packages with distinct execution markers: default A versus explicit B proves actual worker selection, rather than merely checking a parsed option. Verify long and short flags, absolute/relative paths, no-default explicit selection, and no-flag default behavior.

Exercise CLI parallel/timeout overrides and group/target selection against the explicit file without widening timeouts. Invalid-file fixtures must assert nonzero status, requested-path diagnostics, zero package markers and no new successful result artifact. Use a supported permission-aware fixture for unreadability, rather than assuming root cannot read a mode-000 file.

Run targeted and full affected-package verification through `bin/ace-test ace-test-runner`; use the repository test verification workflow for final integration evidence. Do not run the repository's full default suite merely to demonstrate this configuration bug.
