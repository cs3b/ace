# Complete Forgejo delivery capabilities with verifiable outcomes

## Outcome and owner

An authorized caller completes the common PR delivery lifecycle on default and explicitly named Forgejo: canonical or fork source, requested draft, transition to ready, and merge conditioned atomically on the exact reviewed head. The resulting provider receipt binds the selected repository and proves the outcome, including after a lost response. Owner: ace-git-forgejo; public types and CLI remain ace-git. qkb.0 consumes this capability; qkc owns the installed endpoint matrix. One coherent large provider slice, no hidden consumer migration.

## Verified gap and boundaries

At ACE 46b980777, provider.rb create_pull_request rejects a different head repository, does not enforce the requested draft, ready_pull_request refuses, and merge_pull_request refuses atomic expected-head merge. These conservative refusals were valid qk1.0 outcomes, not complete Lab delivery. uj0 fixed repository selection; do not reopen it or introduce raw provider calls into consumers. Existing HttpClient/issue/review APIs are the provider-owned transport precedent. Select a documented supported transport within this provider; do not add a generic bypass, a second public CLI, or a fallback to another server. No change to approval ownership, CI-advisory policy, or release authorization.

## Public contract

- Existing ace-git pr create/show/update/ready/merge, --server/--default-server and --format json remain the public surface. Resolve server/provider/base repository once; retain head repository, head ref, base ref, object number/URL and expected SHA. Reject cross-host or unprovable fork provenance before mutation; a fork is not permission to retarget the selected base repository.
- Create accepts canonical and same-server fork heads and preserves draft:true/false exactly. Existing matching PR is reusable only when repository/ref/head/draft requirements agree; wrong state is an explicit conflict, not silent ready publication. Multiple exact matches are conflict. A failed/uncertain create must not create a second PR on replay.
- Ready operates on that exact PR/head and proves the resulting ready state. Already-ready at the same head is idempotent; a stale head or wrong identity is non-success. A head changed during a non-atomic state transition invalidates acceptance and requires reconciliation, never a forged exact-head receipt.
- Merge requires the selected Forgejo server to atomically reject a different source SHA at mutation time. A pre-read followed by unconditional merge is forbidden. Honor the explicit supported merge method and prove merged status plus merge commit, selected PR and source SHA. An already-merged result is reusable only with authoritative matching evidence. Disabled methods, stale head, closed-unmerged and missing authority are classified refusals.
- Lost response, partial mutation, read failure or contradictory evidence produces ProviderUnknownOutcomeError with non-secret operation identity/reconciliation context. Read back authoritative remote state before reuse; inability to distinguish applied from not applied stays uncertain. Never replay an uncertain mutation automatically. Mutations are serialized/attributed through the existing caller's attempt journal; no provider-local execution ledger.
- Capability/version mismatch fails closed before mutation where discoverable. Document the minimum supported server/transport combination from official API evidence and validate it in implementation. An endpoint that cannot supply required atomicity remains unsupported and blocks qkb.0/qkc acceptance; it never authorizes an unsafe workaround or a falsely completed task.
- JSON uses existing normalized evidence/error categories; text explains the failed capability or identity. Auth/offline/malformed/absent/ambiguous/stale remain distinct non-successes, no secret tokens in messages. Dry-run/read-only paths cannot mutate. No compatibility aliases.
