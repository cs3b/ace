# Preserve Herdr pane pointer provenance and classify materialization failures

## Outcome and evidence

A caller reuses or replaces a prepared pane on a foreign/native tab without turning its pointer record into invented window ownership. A failed native tab materialization reaches the public CLI as a classified error. Owner ace-herdr; consumers k86.3 and existing CLI. One small behavioral repair of delivered k86.2, whose historical acceptance is retained.

At 46b980777, RuntimeAdapter#record_prepared_pane rewrites every matching record with root/preset keys even when it originally had neither. read_identity then treats root:nil/preset:nil as provenance and conflicts with a real root. Support#translate_errors omits the sibling TabMaterializationError, although the runtime adapter already translates it. These are two observed entrypoint defects; no new ownership or runtime policy is requested.

## Contract

- Pointer-only records retain only their existing non-ownership meaning across prepared-pane death, replacement and adapter/process restart. Reusing the retained live pane must not split again. Creating a replacement updates its pointer without claiming root/preset provenance.
- A real root/preset record retains its exact verified provenance when its pane changes. Wrong tab ID, conflicting root/preset, unreadable provenance and stale target cannot acquire authority through the repair. Native live evidence remains required by the existing ensure-window contract; no force, broad adoption, null-root fallback or compatibility migration.
- Existing public tab CLI reports TabMaterializationError through the standard Ace::Support::Cli::Error boundary (nonzero, actionable message, no unhandled stack trace in ordinary mode). Runtime callers retain existing runtime classification. Do not report success for a failed tab or destroy a foreign tab during cleanup.

## Acceptance

- [x] SC1: Prepare a pane on a foreign tab, terminate it, recreate it using a fresh adapter/process, then ensure the tab at its verified native root. Record remains pointer-only and a later instance reuses the live replacement without another split.
- [x] SC2: Repeat with genuine owned provenance; it is preserved. Wrong ID, conflicting root/preset and corrupt provenance cannot bypass existing conflict/ownership guards. Include a valid native-root negative control and persistent-record shape assertion tied to the behavior.
- [x] SC3: Cause a native materialization failure through the real CLI entrypoint; it exits nonzero with the standard error and no false success or foreign resource deletion. Verify the runtime adapter still emits its documented runtime error.
- [x] SC4: Run ace-herdr all and affected runtime/CLI tests, then ace-test-suite; independent exact-source review. k86.3's installed Herdr consumer acceptance must include the SC1 sequence; product unit fixtures alone do not establish installed readiness.
