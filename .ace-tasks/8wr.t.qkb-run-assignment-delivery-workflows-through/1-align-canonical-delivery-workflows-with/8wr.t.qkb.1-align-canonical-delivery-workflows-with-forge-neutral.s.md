# Align canonical delivery workflows with forge-neutral evidence

## Observable result

A fresh agent outside the ACE checkout loads the canonical delivery workflow and follows one provider-neutral vocabulary on GitHub or Forgejo. Every step uses the qkb.0/qk1 interfaces and qjl evidence; role routing and publication decisions remain explicit.

## Interface and consumers

- Canonical PR workflow/skill names are `wfi://git/pr/create`, `wfi://git/pr/update`, `/as-git-pr-create`, `/as-git-pr-update`; remove `wfi://github/pr/create`, `wfi://github/pr/update` and GitHub-specific skill names, registries and source references, with no forwarding aliases. qkb.0 introduces executable final step artifacts; this slice completes canonical ownership, catalog, projections and documentation.
- Consumers include ace-assign presets/catalog/prepare/drive, ace-git-worktree task setup, ace-review PR workflows, ace-task draft/review/work instructions, ace-overseer, ace-handbook integrations and source nav registrations. Update sources in their owning packages and normal generated projection paths during implementation; no new harness-native skill tree.
- PR workflow input carries reviewed task, exact qjl attempt, selected forge and explicit qkb.0 provenance. Create/update use neutral PR CLI; readiness and integration require current test/review receipts. Output preserves exact server/repository/PR/head and allowed next action. No instruction requires manual translation into gh/fj or assumes github.com.
- Role handoffs use qk0 charter and qjx service capability contract: worker implements, independent reviewer judges, integrator merges and administrator performs scoped privileged operations. No Python lab/labd commands, permanent Lab Work graph, fixed pane IDs or credential-implies-authority wording remains.
- A missing authorized service or required evidence produces a routed blocker. Coordinator remains responsive; long execution/review uses assigned delegates instead of blocking conversation.
- Publication, deployment, synchronization and privilege operations consume a valid authorization for that exact operation: direct Captain approval, an applicable scoped standing authorization, or a resolved qjz proposal. Do not create a new proposal for an already authorized operation. When valid authorization is absent, create a precise qjz proposal; confirmed Telegram delivery starts the 16-hour no-reply window, and every precisely presented proposal is eligible, including high-privilege actions. All paths retain exact scope/tests/review/SHA/OTP gates. Merge authorization alone does not authorize publication or any different operation.
- CI is advisory everywhere, including failure examples. Existing review quality requirements remain; actual synthesis/test failures or stale heads cannot be ignored. Version/changelog preparation is not publication and must not prevent normal delivery from ending at authorized merge.

## Success criteria and verification

1. Fresh installed environment resolves both new wfi and skill sources outside the repository; old names fail with clear unknown-source behavior, not aliases. Use `ace-nav resolve` and `ace-bundle` on final sources from a temporary external directory after package install.
2. Trace equivalent GitHub/default Forgejo/named Forgejo delivery and both provenance modes with the final workflow names; each stage consumes available neutral commands and emits qjl evidence. Use deterministic workflow fixtures and one integrated assignment run from qkb.0.
3. Inventory active canonical assets across named consumers; no hidden gh, fixed hostname, Python lab/labd or mandatory-green-CI correctness direction remains. Historical audit/docs examples are explicitly classified rather than broad text deletion.
4. Simulate wrong SHA, missing reviewer/service/OTP, uncertain merge and red-CI-only cases. Required technical failure yields a blocker; red CI alone does not. No release happens solely because merge succeeded.
5. A valid direct approval or scoped standing authorization dispatches the matching operation without a redundant proposal; missing or out-of-scope authorization creates a qjz proposal instead. Test all three authorization paths and a scope mismatch, retaining technical gates in each.
6. Skills still install under `.agents/skills` and normal nav bundle resolution works from fresh contexts. The new source names appear in usage/catalog help and remove obsolete dependencies.

Run `ace-test ace-assign all`, affected handbook/nav/overseer package suites and `ace-test-suite`. Record source/projection versions, executed command outputs and independent verdict for qkc/l2d.7. Do not claim packaging proof merely because a source file exists.

## Boundaries and defaults

Single end-to-end adoption slice; advisory size: large. Depends on qkb.0, qk0, qjx and qjz contracts. No new scheduler, ledger, role policy or Lab local deployment ownership; lab-overseer gc0 and lab-config gad.5 install/adopt local charters. No live delivery, release or external message is performed during specification work. No unresolved product question.

The final neutral workflow entrypoints, all catalog consumers and removal of old GitHub-specific names ship together; no intermediate installed release exposes mixed vocabularies or compatibility aliases.
