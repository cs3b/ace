`with_execution_slots(mapping_ids:, candidate_deployment:)` validates original/candidate mapping and physical-slot ownership. Existing mapping IDs retain their project, journal, authority state-root and slot association. Recycled physical identities, ambiguous lock aliases and omitted changed/added/removed mappings refuse. Changes to the fixed project or authority also make their mappings mandatory. Removed original selections remain bound to their original descriptor; added fresh slots use staged fixed selections. A same project ID cannot substitute its new journal for old history.

The existing normal admission `with_slot` and maintenance use identical exclusions under canonical authority state root and slot key. Maintenance acquires them lexically and unwinds in reverse, checks protected private roots, then pins one readable real commit per exact journal identity. Frozen contexts are sorted by mapping ID, contain exactly mapping_id/journal/commit and live only inside the held owner invocation. Recursive entry refuses before acquiring any lock or mutex. Changed refs raise Conflict. Missing roots/commits or substituted journals refuse before yielding.

Maintenance eligibility currently checks that exact live context/ref and then refuses with EvidenceUnavailable because complete original retained authentication and current actual inventory verification remain unimplemented.
