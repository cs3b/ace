# Enforce the authorized OTP expiry at consumption

## Outcome and ownership

An authorized requester receives an OTP only while its exact challenge remains valid. Delivery shortly before expiry cannot extend the authorized window. Owner: ace-hitl; consumers: Hermes y24, HITL vs2, and the lab-config:gad.b publisher later exercised by vs3. This small repair preserves 34i's delivered authenticated IPC and does not claim to implement publisher authorization.

## Verified gap

Code-path review at ACE `686abe359` found MemoryVault#write uses delivery time plus its default fifteen-minute TTL, without the request's otp.expires_at. Store#consume verifies operation name and vault state but never the challenge deadline. The current expired-challenge test checks deliver only. This finding is code-path verified, not a newly executed reproduction. The first implementation test must deliver before a short challenge expires, advance controlled time beyond that challenge, and reproduce the incorrect successful consumption before the fix.

## Behavior and public contract

- Existing `consume ID --operation NAME [--timeout SECONDS]`, Client#consume and Store#consume keep their signatures. The challenge's persisted expires_at is authoritative; vault retention may shorten, never extend, this window.
- At the locked secret handoff, now >= challenge expiry refuses with a classified OTP-expired/state error requesting a fresh challenge. No OTP bytes or success receipt are returned, no business effect is attempted, and repeat consume cannot recover the expired secret. Apply the same rule through service and supported direct-store use; a vault implementation cannot bypass it.
- Recheck validity at handoff, including a consume that began before expiry and waited for delivery. A code delivered while valid but consumed after expiry is rejected. Duplicate delivery or replay does not reset challenge lifetime.
- Expiry revokes only that secret challenge, not the enclosing assignment, non-secret HITL request policy or business authorization. Requester explicitly creates a fresh authorized challenge; no automatic operation retry, blanket timeout cancellation or secret persistence is introduced.
- Continue rejecting foreign requesters, wrong operations and ended attempts. Before expiry the rightful requester receives the code once; consumed retries retain secret-free terminal behavior. Vault eviction/restart never restores a code or extends the recorded deadline. Logs/public projections contain no raw code or hash.

## Success criteria and verification

- [ ] SC1: Controlled time proves before/exactly-at/after challenge expiry, including a challenge shorter than vault TTL and vault TTL shorter than challenge. Acceptance ends at the earlier bound without slow wall-clock sleeps.
- [ ] SC2: Exercise delivery just before expiry, consumption begun before expiry but handoff after, duplicate delivery, repeated consume and service/vault restart. Expired outcomes contain no secret and never become consumed success.
- [ ] SC3: Through authenticated service/client IPC, prove one valid same-request/operation transfer and an expired refusal; foreign requester and wrong operation remain rejected. Test the direct-store entrypoint too so changing vault type cannot weaken the deadline.
- [ ] SC4: Run `bin/ace-test ace-hitl all`; retain exact-source tests and independent review. Installed Telegram/publisher acceptance remains with y24/vs2/vs3 and lab-config:gad.2; deterministic local evidence cannot replace it.
