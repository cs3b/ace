# Spike ACE tmux additive read-side delta after shipped runtime/control work

## Objective

Validate the remaining additive read-side delta after the shipped tmux runtime/control work landed, including whether anything beyond the current `ace-tmux list` contract is still needed.
This spike does not assume `ace-tmux state`, and it does not own recording/provenance or recording artifacts. Interactive control questions belong to sibling task `8re.t.n1d`.

## Behavioral Specification

### User Experience

- A designer or implementer can answer, from one spike outcome, what the current `ace-tmux list` surface already guarantees and what genuine read-side gap remains.
- A designer or implementer can answer whether a machine-readable runtime surface is needed and how it should extend `list`.
- The spike produces a concept inventory that reflects shipped tmux behavior instead of stale speculative contracts.
- The spike treats recording inheritance, provenance, and artifact layout as already deferred out of this task.
- The spike does not answer interactive control questions such as live send, wait, attach, detach, or pane-tail capture semantics.

### Expected Behavior

1. The spike validates one coherent baseline scenario for generic runtime inspection through shipped `ace-tmux list` behavior.
2. The spike explicitly identifies which original `8r6.t.xeu` concepts are already superseded by shipped work and which remain valid additive follow-up candidates.
3. The spike explicitly identifies the minimum new concepts, if any, required for reusable runtime state beyond today’s table output.
4. The spike keeps recording artifact scope, recording inheritance, and `source_scope` provenance out of scope.
5. The spike produces a concept inventory table showing concept status as kept, changed, new, or rejected.
6. The spike defers further subtask drafting until the inventory makes later decomposition stable.
7. The spike confirms the inspectability surface is generic and not owned by visible-fork-specific behavior.
8. The spike rejects any attempt to absorb interactive control semantics that belong to sibling task `8re.t.n1d`.

### Interface Contract

- **Spike output contract**
  - Updated parent task concept inventory and scope notes
  - Clear go/no-go statement for these behavioral contracts:
    - shipped `ace-tmux list` runtime inventory baseline
    - optional machine-readable runtime output, if still needed
    - generic session/window/pane identifiers and any added liveness hints
    - explicit rejection of interactive control command ownership
- **Decision contract**
  - The spike does not implement code.
  - The spike may refine task specs and usage draft content if the validated contract differs from the initial draft.
  - The spike treats visible-fork launch and fork-window behavior as out of scope and owned by sibling task `8r6.t.u53`.
  - The spike treats interactive control commands and live pane-tail capture as out of scope and owned by sibling task `8re.t.n1d`.

### Success Criteria

- [ ] One validated baseline scenario exists for generic tmux runtime inspection using current shipped behavior.
- [ ] The spike identifies which current inspectability concepts survive unchanged, which are extended, and which are newly introduced.
- [x] Recording scope, recording source-scope reporting, and artifact layout ownership are deferred out of this task.
- [ ] The spike leaves no ambiguity about the boundary between any future persisted artifact reporting and live control-side pane-tail capture.
- [ ] The parent task can be safely decomposed into implementation subtasks after the spike.
