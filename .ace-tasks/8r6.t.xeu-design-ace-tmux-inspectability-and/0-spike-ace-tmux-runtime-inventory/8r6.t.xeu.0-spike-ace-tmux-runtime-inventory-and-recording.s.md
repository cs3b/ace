# Spike ACE tmux additive read-side delta after shipped runtime/control work

## Objective

Validate the remaining additive read-side delta after the shipped tmux runtime/control work landed and record whether anything beyond the current `ace-tmux list` contract is still justified in the current repo state.
This spike does not assume `ace-tmux state`, does not own recording/provenance or recording artifacts, and does not draft a new implementation task unless a concrete consumer need is found. Interactive control questions belong to sibling task `8re.t.n1d`.

## Behavioral Specification

### User Experience

- A designer or implementer can answer, from one spike outcome, what the current `ace-tmux list` surface already guarantees and that no additional CLI read-side surface is justified today.
- A designer or implementer can answer that any future machine-readable runtime surface must be reopened by a concrete consumer rather than carried forward as a speculative contract.
- The spike produces a concept inventory that reflects shipped tmux behavior instead of stale speculative contracts.
- The spike treats recording inheritance, provenance, and artifact layout as already deferred out of this task.
- The spike does not answer interactive control questions such as live send, wait, attach, detach, or pane-tail capture semantics.

### Expected Behavior

1. The spike validates one coherent baseline scenario for generic runtime inspection through shipped `ace-tmux list` behavior.
2. The spike explicitly identifies which original `8r6.t.xeu` concepts are already superseded by shipped work and which remain valid today.
3. The spike explicitly identifies that no additional CLI read-side concepts are justified beyond the current table output in the current repo state.
4. The spike keeps recording artifact scope, recording inheritance, and `source_scope` provenance out of scope.
5. The spike produces a concept inventory table showing concept status as kept, rejected for now, or deferred.
6. The spike does not recommend new implementation work from the current repo state.
7. The spike names one explicit closure/archive outcome task so the task family does not end with an implied “reopen later” path.
8. The spike confirms the inspectability surface is generic and not owned by visible-fork-specific behavior.
9. The spike rejects any attempt to absorb interactive control semantics that belong to sibling task `8re.t.n1d`.

## Spike Outcome

### Decision Summary

- **Read-side baseline**: `ace-tmux list` is the shipped generic runtime inventory surface for sessions, windows, and panes.
- **Machine-readable CLI follow-up**: no-go for now. No current repo consumer justifies a new `ace-tmux list --format ...` mode.
- **Additional liveness hints**: no-go for now. Active markers, identifiers, current command, and working-directory basename are sufficient for the current repo state.
- **Recording/provenance**: deferred out of task.
- **Interactive control ownership**: rejected from this task and remains with sibling task `8re.t.n1d`.

## Outcome Tasks After Spike

- `8r6.t.xeu.1` closes the task family by synchronizing the parent task, task-local usage guidance, and public `ace-tmux` usage docs around the no-go result, rerunning the parent review, and preparing the parent for archive.

### Validated Baseline Scenario

An operator or higher-level ACE tool can inspect live tmux runtime state through the shipped public CLI:

```bash
ace-tmux list
ace-tmux list --windows
ace-tmux list --sessions
```

This baseline is backed by shipped code in `ace-tmux/lib/ace/tmux/cli/commands/list.rb` and `ace-tmux/lib/ace/tmux/organisms/control_surface.rb`, plus fast and E2E coverage for the `list` scopes. The current repo state shows that:

- pane rows already expose active marker, pane id, resolved target, current command, and working-directory basename
- window rows already expose active marker, tmux window id, session/index, name, and pane count
- session rows already expose session name, attached-client count, and window count
- current in-repo structured consumers use Ruby APIs or local metadata rather than a shared CLI JSON schema
