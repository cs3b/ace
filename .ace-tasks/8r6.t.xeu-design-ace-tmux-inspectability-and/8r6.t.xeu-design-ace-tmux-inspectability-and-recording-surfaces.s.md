# Design ACE tmux read-side follow-up after shipped runtime/control work

## Objective

Define the remaining read-side follow-up for `ace-tmux` after the shipped tmux control/runtime work, using the current public surface as the source of truth instead of the original speculative `ace-tmux state` design.
This task does not own live control commands. `send`, `capture`, `wait`, `attach`, and `detach` are already shipped and remain owned by sibling task `8re.t.n1d`.

## Behavioral Specification

### User Experience

- A user or higher-level ACE tool can inspect live tmux runtime state through the shipped `ace-tmux list` surface without shelling directly to raw `tmux`.
- Operators can identify current sessions, windows, and panes using the existing table output and any additive read-side metadata this follow-up eventually introduces.
- Any future read-side expansion must build on the live tmux contract already used by `ace-assign`, `ace-demo`, and direct operator flows.
- Visible fork execution may consume the read-side surface, but this task must not redefine visible-fork launch behavior or callback behavior already shipped elsewhere.
- Recording/artifact provenance is explicitly unresolved and blocked on review questions above; it must not be treated as an accepted contract in this draft.

### Expected Behavior

1. The baseline read-side surface remains `ace-tmux list` and reflects the current shipped CLI.
2. Current runtime inspection continues to expose sessions, windows, and panes with identifiers, active markers, current commands, and working-directory context.
3. If this task later adds richer read-side metadata, that addition must be explicitly additive to the shipped contract and justified by a consumer need.
4. Any future machine-readable surface must align with the existing `list` scopes unless a separate command is explicitly chosen during review.
5. The task remains generic and independent of `ace-assign`-specific runtime truth, even though `ace-assign` may consume its output.
6. The task does not promise recording flags, recording inheritance, persisted tmux artifacts, `source_scope`, or semantic interpretation unless a later rewrite resolves those review questions.
7. Interactive control commands such as `send`, `wait`, live pane-tail `capture`, `attach`, and `detach` remain out of scope here and are already owned by sibling task `8re.t.n1d`.

### Interface Contract

- **Current `ace-tmux` CLI contract**
  ```bash
  ace-tmux list
  ace-tmux list --all-panes
  ace-tmux list --windows
  ace-tmux list --sessions
  ace-tmux list --session dev --window work
  ```
- **Current `ace-tmux list` output contract**
  - Reports live tmux sessions, windows, or panes according to the selected scope.
  - Pane rows include active marker, pane id, resolved target, current command, and working-directory basename.
  - Window rows include active marker, tmux window id, session/index, name, and pane count.
  - Session rows include session name, attached-client count, and window count.
- **Unresolved follow-up contract**
  - Whether to add a machine-readable read-side interface remains open.
  - Whether tmux recording/provenance belongs here remains open.
- **Consumer contract**
  - Other tools such as `ace-overseer` and `ace-assign` may consume the generic read-side surface but must not redefine its schema in their own task specs.
  - Sibling task `8re.t.n1d` owns interactive control semantics and consumer control integrations.
  - Any future extension here must not redefine the already-shipped control-side pane-tail behavior in `capture`.

### Success Criteria

- [ ] The task is rewritten around the shipped `ace-tmux list` baseline instead of the unimplemented `ace-tmux state` proposal.
- [ ] The task clearly distinguishes current shipped behavior from future additive read-side work.
- [ ] The task resolves whether recording/provenance remains in scope or is split into a separate task.
- [ ] Any future read-side addition is generic enough for `ace-overseer`, `ace-assign`, and direct operator use without depending on visible fork semantics.
- [ ] Draft usage guidance exists for the revised read-side follow-up contract.
- [ ] The task explicitly excludes already-shipped control-side commands owned by `8re.t.n1d`.
