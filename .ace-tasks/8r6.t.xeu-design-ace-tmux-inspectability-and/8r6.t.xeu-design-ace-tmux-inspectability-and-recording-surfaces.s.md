# Close ACE tmux speculative read-side follow-up after shipped runtime/control work

## Objective

Record and close the validated no-go outcome for speculative tmux read-side follow-up work after the shipped tmux control/runtime work, using the current public surface as the source of truth and explicitly retiring this task family instead of leaving it open-ended.
This task does not own live control commands. `send`, `capture`, `wait`, `attach`, and `detach` are already shipped and remain owned by sibling task `8re.t.n1d`.

## Behavioral Specification

### User Experience

- A user or higher-level ACE tool can inspect live tmux runtime state through the shipped `ace-tmux list` surface without shelling directly to raw `tmux`.
- Operators can identify current sessions, windows, and panes using the existing table output without needing a new read-side CLI feature today.
- This task family closes with a no-go result because no concrete consumer currently justifies additive read-side CLI work beyond the shipped contract.
- Any future read-side expansion must be drafted as a new task family rather than reopening this archived one.
- Visible fork execution may consume the read-side surface, but this task must not redefine visible-fork launch behavior or callback behavior already shipped elsewhere.
- Recording/artifact provenance is out of scope for this task and may be drafted separately later if a concrete consumer needs it.

### Expected Behavior

1. The baseline read-side surface remains `ace-tmux list` and reflects the current shipped CLI.
2. Current runtime inspection continues to expose sessions, windows, and panes with identifiers, active markers, current commands, and working-directory context.
3. No richer read-side CLI metadata is justified in the current repo state beyond the shipped `list` contract.
4. This task family closes through an explicit archive/no-go path rather than leaving future decomposition implied.
5. Any future machine-readable surface must align with the existing `list` scopes and be drafted in a new task only if a concrete consumer later requires it.
6. The task remains generic and independent of `ace-assign`-specific runtime truth, even though `ace-assign` may consume its output.
7. The task does not promise recording flags, recording inheritance, persisted tmux artifacts, `source_scope`, or semantic interpretation.
8. Interactive control commands such as `send`, `wait`, live pane-tail `capture`, `attach`, and `detach` remain out of scope here and are already owned by sibling task `8re.t.n1d`.

### Interface Contract

- **Current `ace-tmux` CLI contract**
  ```bash
  ace-tmux list
  ace-tmux list --all-panes
  ace-tmux list --windows
  ace-tmux list --sessions
  ace-tmux list --session dev --window work
  ```
- **Current `ace-tmux list` output contract**
  - Reports live tmux sessions, windows, or panes according to the selected scope.
  - Pane rows include active marker, pane id, resolved target, current command, and working-directory basename.
  - Window rows include active marker, tmux window id, session/index, name, and pane count.
  - Session rows include session name, attached-client count, and window count.
- **No-go outcome contract**
  - Current repo evidence does not justify a machine-readable read-side CLI interface.
  - This task family closes without new implementation follow-up.
  - If a future consumer reopens this space, any such interface must be drafted as a new task and should extend `list`; this archived task does not re-open recording/provenance ownership.
- **Consumer contract**
  - Other tools such as `ace-overseer` and `ace-assign` may consume the generic read-side surface but must not redefine its schema in their own task specs.
  - Sibling task `8re.t.n1d` owns interactive control semantics and consumer control integrations.
  - Any future extension here must not redefine the already-shipped control-side pane-tail behavior in `capture`.
