# Admit receipt key rotation under exclusive inbox context

## User experience and outcome

A deployment-controlled maintainer attempts receipt-key replacement in a protected inbox context. ACE grants exclusive rotation admission only after all context events are completed and all admitted operations have positively ended. Unresolved/corrupt/inaccessible state refuses with the current key unchanged. Fresh enqueue pins the new public-key fingerprint only after admitted atomic commit. Advisory size medium; real end-to-end rotation admission, not research-only work.

## Public interface contract

Fixed authenticated ACE inbox-context endpoint, selected by root-installed map, exposes `begin_rotation(context_id, expected_key_generation)` to maintenance_uids only and returns rotation_id/current fingerprint/generation or refusal. Context owner obtains exclusive context lock before scanning all events and rejects any unresolved state or outstanding signing admission. The caller cannot select another context/store, bypass with force or rewrite existing fingerprints. `commit_rotation(rotation_id, expected_key_generation, new_public_key_bytes, installed_config_digest, signer_keypair_attestation)` verifies configured protected public-key path/config now contain the supplied bytes, signer attests matching private pair through its fixed authenticated account, and updates current context key generation under the held lock. Private bytes never transit ACE/public API. Maintenance performs domain installation only within this admitted interval; lock remains held through readback/commit. `abort_rotation(rotation_id)` retains old validated public config/generation after positive rollback readback, never frees an unverified partial replacement. Status reports blocked/uncertain if installation/rollback cannot be verified.

Enqueue/deliver/observe-to-sign/reconcile clients acquire `begin_context_operation(context_id, purpose, event_id, process_binding)` shared admission, returning operation_id/key_generation. Lock ordering is context admission first, then task/assignment lifecycle exclusion, attempt cache, Herdr event lock; rotation does not acquire assignment/event locks while another shared admission can be held. Signer holds admission through exact proof submission/consumer response and `end_context_operation(operation_id)`. Fixed current peer UID/process OS birth authorizes end; stale admission/key generation cannot reconcile. The owner maintains active admission records in existing Herdr context control metadata, not a new delivery ledger. On client disconnect/deadline, it refuses further action but does not silently clear unknown signing/maintenance ownership; owner positively verifies exact process termination/no remaining admitted writer, or trusted maintenance records verified abort. 30s deadline reports blocked, never manufactures quiescence. Timeout cannot allow rotation while an old signer process may still submit accepted proof. Losing owner process reconstructs admission records before opening context; unknown admission stays blocked. Private key replacement and atomic rollback/readback belong to gad.8 installer, which must consume these public admission IDs. Generic mechanism cannot invoke arbitrary installer commands or choose private-key paths.

## Scope and ownership

This child owns reusable ACE context admission/key-generation API and its integration into every enqueue/deliver/sign/reconcile path, including direct CLI entry points. xz9.0 supplies authenticated cross-user transport. gad.8 supplies protected key installation, paired replacement/rollback and actual install proof; gad.b signer participates in the admission protocol. Source prerequisites are xz9.0/y23; gad.8/gad.b are downstream consumers, preventing source/install dependency cycles. No retention/16h policy change or per-request trust-root switching.

## Success criteria

- [ ] SC1: Distinct authorized maintenance UID rotates an empty/all-completed fixture context while all other mutations are excluded; next enqueue pins the new fingerprint and old events remain byte-identical.
- [ ] SC2: queued/claimed/uncertain/delivered/requeued, corrupt/inaccessible events or any live/unknown signer admission refuse rotation with no key/config transition.
- [ ] SC3: Enqueue/sign/reconcile racing rotation cannot use mixed key generations; stale operation/rotation token conflicts and unauthorized worker/direct CLI cannot bypass admission.
- [ ] SC4: Crash/disconnect/partial install requires verified original-pair rollback or blocked uncertain state; restart preserves pinned fingerprints and active admissions without guessing quiescence.
