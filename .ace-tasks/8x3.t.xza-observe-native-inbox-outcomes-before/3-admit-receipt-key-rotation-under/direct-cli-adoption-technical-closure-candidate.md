# Direct Inbox CLI adoption — technical closure candidate

Draft for independent readiness review, based on `623aa67e4`. This resolves the three decisions in `direct-cli-adoption-review-input.md`; it does not promote xza.3, implement interfaces, or claim installed acceptance. Existing admission, rotation and canonical reconciliation checkpoints remain valid within their recorded limits.

## Observable supported flow

Protected `ace-herdr inbox enqueue`, `deliver`, `status` and `reconcile` use authenticated installed selection before constructing any local Inbox or reading payload/proof files. Enqueue/deliver run in the fixed context owner; reconciliation reaches the existing protected authority operation. Standalone callers retain existing local behavior only after trusted classification says ordinary. Unsupported protected roles, unavailable selection and unknown effects refuse without local fallback. Refusal alone does not satisfy this adoption task: all positive flows below must execute.

Examples (existing `inbox` namespace, JSON output):

```text
ace-herdr inbox enqueue --project PROJECT --mapping MAP --inbox-context CONTEXT \
  --event EVENT --attempt ATTEMPT --ref reverse.json --file payload.txt
ace-herdr inbox deliver --project PROJECT --mapping MAP --inbox-context CONTEXT \
  --event EVENT --attempt ATTEMPT --claim-generation 0
ace-herdr inbox status --project PROJECT --mapping MAP --inbox-context CONTEXT \
  --event EVENT --attempt ATTEMPT
ace-herdr inbox reconcile --project PROJECT --mapping MAP --inbox-context CONTEXT \
  --assignment ASSIGNMENT --attempt ATTEMPT --event EVENT --receipt proof.json \
  --mutation MUTATION --expected-generation GENERATION --receipt-key-sha256 ORIGINAL_KEY_SHA
```

Selection, assignment, attempt, event and mutation IDs use their existing bounded colon-free token rules; operation IDs retain their existing fixed hexadecimal rule. Reverse Ref session/pane values retain the existing Ref token and native address rules, which allow colons; do not apply the selection/event ID restriction to them. `claim-generation` and authority `expected-generation` are distinct strict nonnegative integers. All protected selectors are required and hints must agree exactly with explicit arguments. No endpoint/store/key path, actor, UID, force, generation refresh or completion boolean is accepted. Existing standalone options are unchanged; protected-only options in a genuinely uninstalled ordinary environment refuse.

Their existing bootstrap/source/preparation/runtime proof is required. Expand only the source-owned protected command allowlist for the two read-only modes below. A current publication chooses trusted reader code; it does not choose an event's historical key, authorize native effects or grant a caller role. The accepted entry remains held through each invocation, using the existing descriptor-passed interpreter and manifest, bounded subprocess, empty environment and exact selected wrapper bytes; never PATH, an environment-selected executable, or a reopened wrapper pathname.

Herdr already depends on Runtime and owns BoundedProcess. It may use these existing boundaries to invoke the selected Assign child; it does not import Assign Ruby or add an Assign gem dependency. The child alone interprets Deployment/DeploymentHistory and uses the SAME `ProtectedAssignmentContext#protected_participant?` being implemented for attempt CLI adoption. * `authority inbox-context-selection --project PROJECT --mapping MAP --inbox-context CONTEXT`: one compact JSON line, exactly `{schema,uid,project_id,mapping_id,inbox_context_id,descriptor,history,context,authority}`, schema `ace.assign.inbox-context-selection/v1`, at most16384bytes. descriptor/history are exact held installed immutable `{path,bytes,sha256}` refs. context is exactly `{control_socket_path,owner_credentials,native_mapping_id}`; owner_credentials is `{uid,gid,groups}`. authority is exactly `{authority_id,socket_path,uid,gid,groups}`. IDs/credentials/path bounds use existing Deployment validation. No store/key/private path or grants leave this response.

The child loads and holds current descriptor/history via existing owners, requires history selects current descriptor, resolves the exact project/mapping/context association and matching authority, and verifies the selection unchanged before replying. It does not call authority-only `verify_inbox_context!` as an unprivileged caller and does not inspect private journal/Inbox files. Actual client endpoint authentication and owner authorization remain mandatory afterward. Retained participant with removed current mapping/context refuses. No selection response is accepted from ambient config or another command.

When discovery is absent, Runtime's existing presence checks against installed descriptor/history/publication still force refusal. When discovery exists, classification runs even without protected flags, before file reads or local construction. Entry failure/malformed output/ref drift is refusal; no ordinary fallback. Only genuinely absent installation plus no protected hints, or successful trusted ordinary classification plus no protected hints, permits local mode. Discovery/selection pins live only within the held operation; every new command reselects and authenticates current owners. The context endpoint receives the ACTUAL Herdr process kernel peer, not the selected child's PID or a forwarded UID grant.

## Fixed context effects and bounded ingress

Reuse InboxContextServer/Client and InboxContextOwner's source-selected Inbox. Add fixed `enqueue_context`, `deliver_context` and `status_context` operations; no arbitrary callbacks, executable selection or target filesystem paths. Existing purpose/role grants remain authoritative: source context owner checks actual peer UID/GID/groups/birth and the configured enqueue/deliver/observe purpose. CLI classification never adds a grant.

All three new methods retain the existing closed request envelope `{version,context_id,operation,params}`: version is integer1, context_id must equal the selected server context, operation is the exact fixed method name, and params must have only its method-specific fields below. The metadata frame bound includes this entire envelope. Enqueue params are exactly `{operation_id,key_generation,event_id,attempt_id,reverse,payload_bytes,payload_sha256}`. reverse is exactly the existing normalized Ref `{schema,session,pane}`. `payload_bytes` is a strict JSON integer in1..65536 naming the raw byte length, never content; `payload_sha256` is exactly64 lowercase hexadecimal characters. The <=16KiB strict JSON metadata line ends with its existing newline delimiter; immediately afterward come exactly payload_bytes raw UTF8 bytes, followed by mandatory write-half-close/EOF. There is no payload delimiter, second content field or duplicate encoding. Short body, surplus bytes, digest mismatch, invalid UTF8 or NUL refuses before effect entry. Add a bounded one-part ingress using the existing InboxContextWire framing owner; no base64 expansion or caller filename. Ref/payload files use one held regular no-follow nonblocking bounded handle, strict decoded-duplicate JSON for the Ref, stable handle/path metadata and no NUL. File reads occur only after protected selection. Payload remains subject to existing native limits and managed-envelope rules; this CLI does not invent a managed-envelope or target-authority override.

Deliver params are exactly `{operation_id,key_generation,event_id,attempt_id,expected_claim_generation}` with no raw payload/ref. Status params are exactly `{event_id,attempt_id}` and read-only; require configured purpose visibility and exact retained attempt association. All metadata/proof decoding remains strict depth16 UTF8 JSON with existing size bounds and extra-byte refusal. One original30s absolute context deadline covers frame/body/reply; it never clears an admission or declares no effect. Public record projections remain bounded and do not expose raw payload/native output/private paths.

Direct replies retain the existing version/context/result transport envelope. The result has schema `ace.herdr.inbox-direct-result/v1`. For enqueue_context and deliver_context its exact fields are `{schema,operation,record,admission_state}`; enqueue only returns idle after verified completion, while deliver returns idle or unknown. For status_context exact fields are `{schema,operation,record}`. operation is the exact requested fixed method. The closed record is `{event_id,attempt_id,payload_sha256,receipt_key_sha256,claim_generation,state,origin_target,target,binding,session,pane,submission_intent,wake}`; wake is nil or exactly `{status}` with none/sent/pending. Native target/binding projections retain existing typed target fields and bounds; no receipt native_output, error text, payload, observer prose or private paths leave this result. The client verifies schema, field closure and exact event/attempt association before using it. Public CLI emits that record plus admission_state for effects. This enum is observation only: it cannot authorize native resend, rotation or clearance. CLI sends end only for idle; the owner independently revalidates binding/retained record and in_flight before ending. Unknown delivered/pending-wake remains visibly unknown and retained on exact replay/restart. Reply loss never supplies idle authority.

The CLI acquires existing `begin_context_operation` for the exact enqueue/deliver purpose/event with its captured actual process binding. It retains returned operation_id/key_generation/fingerprint and calls the fixed effect. Admission precedes inventory/event locks. The owner persists original direct-input binding in the EXISTING operation.effect_binding field before any effect and sets in_flight=1. Extend that field to a closed purpose-discriminated direct binding `{schema,purpose,event_id,attempt_id,selection,input_sha256}` with schema `ace.herdr.inbox-direct-effect/v1`. For enqueue, selection is exactly `{reverse,payload_bytes,payload_sha256}` with the normalized Ref and bounds above; for deliver it is exactly `{expected_claim_generation}` with a strict nonnegative integer. The existing reconciliation binding remains its separate exact shape. input_sha256 is the SHA256 of the existing deterministic JSON encoding of `{purpose,event_id,attempt_id,key_generation,selection}`, taking key_generation from the enclosing retained operation. Retain only these original decoded selectors, not raw payload or an outcome copy; this permits exact resumed readback rather than an unverifiable digest-only claim. No payload, outcome copy or new per-event ledger enters control metadata.

The state validator must discriminate these branches explicitly without changing other-purpose invariants. For the new fixed direct enqueue/deliver handlers only, a nil effect_binding is allowed before effect entry with in_flight=0 and completion=nil; direct effect entry atomically persists its binding and in_flight=1. This restriction must not apply to existing with_operation admissions for other purposes, including observe_to_sign, which legitimately persist in_flight=1 without a reconciliation binding. Preserve those existing source-owner and completion requirements unchanged. A direct binding must match the enclosing operation purpose/event, validate its closed schema/selection and recomputed input digest, and have completion=nil; direct completion must not occupy the existing canonical reconciliation completion field. A reconciliation binding keeps its current exact validation and, when in_flight=0, its required verified canonical completion. Do not weaken that existing requirement to accept any idle binding.

For a structurally valid direct binding with in_flight=0/completion=nil, the tuple is only a known-idle candidate, never proof by itself. On resumed begin admission, fixed effect replay and end admission, the source owner must revalidate the retained DeliveryRecord under the existing context→inventory/event lock order before returning idle or deleting the admission. It must recheck exact event/attempt, immutable original payload/normalized reverse/target and the operation's selected key association, using the retained selection and source key owner; enqueue may observe later legal record transitions without rewriting its original association. Deliver additionally rechecks its original expected claim generation against the existing claim/submission-intent/binding state: a read-only older-generation result cannot authorize another effect, and known completion requires the exact source-owned pre-submission refusal or accepted post-operation generation/binding and no unresolved issuer described below. Missing, corrupt, changed or insufficient record evidence refuses and preserves the admission/in_flight/completion metadata; it never silently treats arbitrary idle metadata as effect proof. Only the fixed owner can persist the known-idle transition after its original issuer returns and this readback succeeds. Pure structural validate_state! therefore cannot by itself authorize resumed direct completion.

Owner source effect execution uses the admitted current key from InboxContextKey and `source_inbox!`; no ambient `Inbox.from_config`. It validates event/attempt and immutable target/payload/key association using the existing Inbox/DeliveryRecord owner. Each event is serialized by its existing inventory/event locks. A source-owned in-memory issuer entry prevents concurrent execution for the same operation; exceptions/EOF/deadline never remove durable in_flight. Changing input under a retained operation conflicts. An admission without an effect remains known idle and can be ended; once effect entry is persisted, generic end cannot clear it.

## Positive completion and exact replay from the existing ledger

Enqueue creates the existing queued DeliveryRecord, pinning the admitted key fingerprint. Completion requires exact retained record readback after the write: event/attempt, payload digest, original normalized reverse/target and key fingerprint match the original binding; all writes are durable. Then the owner marks the operation known idle and returns its existing bounded registration/record. A duplicate exact enqueue uses the retained record and cannot create or replace an event. A conflicting request or an old-key event that cannot match current admission refuses without rewriting old fingerprints; status is the historical observation route. If a crash leaves in_flight with no authenticated matching record, retain unknown; absence is not a no-effect certificate.

Protected deliver has an explicit compare-and-effect join on the EXISTING DeliveryRecord claim_generation under its event lock. At generation0 with queued untouched record, expected0 permits the first invocation. Before native submission the existing Inbox owner increments claim_generation and durably persists its existing claim and submission_intent. A replay with an older expected generation returns authenticated retained record only, with no native or wake call. Equal expected generation permits a new invocation only when existing source state is queued and positively pre-submission: no submission_intent, no unknown original issuer and all preceding effects are settled. Future expected generation conflicts. Same event at delivered/completed/uncertain is read-only regardless of expected selector. A deliberate retry after verified pre-submission refusal therefore supplies the returned new generation explicitly; repetition never silently refreshes it.

This comparison must live inside the SAME Inbox event transaction as claim increment, not a status check followed by deliver. Owner can extend the existing source Inbox deliver interface with the internally selected expected generation; no second event lock/controller. The existing submission_intent-before-native-call invariant is unchanged. Saved unknown intent never authorizes native resend. The existing delivered wake-retry convenience must not run on protected replay; a wake effect requires its own source-owned, explicitly selected retry contract and is not delivered by this amendment. A fresh first delivery may retain its existing bounded wake behavior; failure/uncertainty remains recorded.

Known completion means the fixed owner observed its issuer return and revalidated a durable matching post-operation record: queued only with authenticated pre-submission refusal, or delivered/completed with exact accepted binding/generation and no unresolved issuer. It may then clear in_flight, after which the actual original peer explicitly ends admission. The event state still blocks rotation unless completed. Unknown native result, crash during effect, uncertain state or unverified wake retains admission blocked; positive downstream canonical reconciliation or existing reviewed no-writer recovery is required. There is no callback-true clearance, timeout cleanup, caller completion claim or automatic resubmission.

After lost effect/end reply or process restart, exact older-generation deliver inspects only retained DeliveryRecord and outstanding operation metadata. It must not call Inbox#deliver to obtain a replay result, since that method can retry wake. Repeated known enqueue/deliver after end ACK loss can use original immutable record and claim generation without storing a second replay/outcome table. No unbounded completed-operation history is added. Durable unknown admission remains reconstructable and blocks rotation even when a new process reads the event. Clearing an orphan still requires xza.3's existing independently verified original-writer termination/downstream-drain contract; CLI cannot provide that proof.

## Canonical settlement of returned direct issuers — review amendment

Independent readiness decision, 2026-10-08: root reviewed this amendment against the source delivery claim increment and approved the bounded returned-issuer recovery contract, including exact actual claim/owner persistence and crash ordering. Implementation must prove failed admission persistence cannot reach native submission, concurrent same-event claim exclusion, later-proof mismatch, and exact restarted confirmation without lock inversion. This approval does not close pre-return no-writer recovery, actual selected subprocess/producer composition, or the parent task's remaining gates.

The closed existing admission metadata gains source-only issuer_state: nil for existing non-direct admissions and new direct admissions before entry, running when the fixed direct effect binding/in_flight entry is persisted, and returned only after the SAME source Inbox enqueue/deliver invocation actually returns. A thrown exception, ensure execution, transport EOF, deadline, missing in-memory issuer or owner restart cannot produce returned. Persist returned before subsequent readback/response; keep it with unknown in_flight when the native result or wake remains uncertain. Validate the exact phase against direct versus reconciliation binding and existing fields; this is operational admission evidence, not a second outcome ledger, native completion proof or caller option. Revise the source control schema/closed fields explicitly; reject obsolete control shapes rather than migrate or infer this evidence.

The ordering is exact: commit binding+running before invoking the source effect; let the source invocation return; commit returned under the same context transaction owner; only then perform final retained-record readback, commit known idle if justified, and send the response. Returned does not mean that delivery succeeded or that a pending wake completed. It records that this particular fixed source invocation finished, including its existing bounded native transport cleanup obligations. Do not mark returned before that cleanup finishes. An exception after the effect but before the invocation returns, or death between invocation return and the returned commit, leaves running. Death after the returned commit but before readback/idle/response leaves durable returned+unknown and is recoverable by the canonical proof branch below; neither the old caller nor old context owner must remain alive for that branch. A replacement context owner must still acquire the existing exclusive store ownership and freshly authenticate the confirming authority; owner replacement alone is never evidence of issuer return.

The SAME fixed confirm_context_completion method and unchanged canonical InboxContextCompletionClient proof query may retire direct admissions after authenticated canonical consumed/superseded settlement. The proof must bind exact context/event/attempt, original payload/key registration, native claim/binding, immutable receipt/signature imports and canonical reconciliation/reply. Match each direct admission's original key generation and input binding against that retained record. For delivery, equality with the exact admitted invocation claim is mandatory; a merely greater generation never identifies this issuer.

The source Inbox owner prepares the fresh claim under the existing context→event lock order, separates that preparation from native submission, and retains a unique source-owned claim_owner bound to this context/operation. The actual event claim increment is exactly expected_claim_generation+1 for initial, pre-submit-rejected, and canonically superseded current-generation dispatch. Persist the actual resulting claim generation and claim_owner in the existing admission before any native submission. An expected next generation is only an expectation until the SAME locked event mutation actually creates that claim; it is not admitted-claim evidence. The subsequent source submission reacquires the event exclusion and revalidates the exact prepared claim/owner/native binding before persisting submission intent or calling native transport. No event→context callback or inverted lock order is permitted. If preparation creates the event claim but the admission update fails, native submission cannot start; retain the running admission for verified recovery. Older-generation or already-settled observational calls create no claim and retain no admitted native claim. A canonical proof cannot settle such an observational admission by borrowing a later claim; its return/readback follows the independent no-effect path.

Canonical confirmation requires proof claim == admitted claim, plus exact retained claim-owner lineage and native binding for this operation, issuer_state=returned, no live in-memory issuer, and a fresh locked retained-record readback agreeing with the proof's claim/state/native binding/key. Enqueue has no native claim: match its exact event/attempt/key/payload/reverse origin and returned enqueue invocation without inventing a delivery generation. Retire only matching admitted IDs in the same existing metadata transaction; an original token then refuses permanently and cannot authorize another effect. No caller UID substitution, native resend, journal mutation or extra retirement ledger occurs. A running/absent issuer-return proof remains blocked even if the event later appears settled; original writer termination/downstream drain still needs its separate verified recovery contract.

A genuine consumed proof does not close the crash-before-returned gap: it proves native consumption of the selected claim, not that every admitted issuer or pending native transport has stopped. Such a running admission requires the existing task's separately verified termination/no-surviving-writer or trusted maintenance abort path, bound to this exact context/operation, issuer and downstream writer scope. Canonical release of an unrelated worker scope, a missing process, a store lease acquired after restart, or a timeout is insufficient. This amendment does not invent a no-writer verifier or claim that the current context owner already implements one. That recovery path remains mandatory family work and an explicit acceptance gap; ordinary caller death or lost reply after durable returned must nevertheless recover through proof-only confirmation without waiting for that separate path.

Preserve current confirmation of a retained reconciliation admission and its canonical completion field shape/peer checks. Also define an idempotent proof-only confirmation branch when that original reconciliation admission has already ended: authenticate the actual installed authority peer and reverify the exact original canonical proof, then retire only eligible matching returned direct admissions, without recreating the old reconciliation admission or granting a new effect. An existing foreign or unresolved reconciliation admission must not be bypassed by this branch. The fixed Endcap reconciliation consumer performs this original-proof confirmation on fresh and exact replay, including replay with a newly admitted idle authority session, then ends only its own positively idle admission. This closes the case where canonical acceptance precedes the direct issuer's returned marker; exact replay can later settle that returned admission without repeating an effect.

Confirmation replay always re-queries the original accepted canonical completion and revalidates the retained event under the same exclusions. An already retired matching direct admission is a successful no-op; any remaining running or mismatching admission is preserved. A crash before the retirement transaction commits leaves the original admissions available for exact replay, while a crash after it commits leaves the old tokens permanently absent. Neither branch changes the accepted canonical reply/completion digests or republishes imports. Proof replay may therefore retire a newly returned matching issuer after an earlier confirmation, but it cannot treat prior confirmation as a general authorization to clear later, unrelated admissions.

After that canonical confirmation, an authenticated signed superseded record may remain queued with no submission_intent and last action reconcile-superseded. The source delivery predicate must accept this as positively settled for a new explicit current claim-generation invocation, alongside initial generation0 and verified pre-submit-rejection. Require exact signed-reconciliation event/attempt/claim/payload/native binding and no preceding unresolved admission/issuer under the existing context/event locks. The original older selector still observes only; it cannot silently refresh or resend. A verified replacement target follows the existing Inbox reconciliation/observation owner, never a caller-supplied direct target override. Queued supersession does not permit receipt-key rotation; the existing completed-retained-event gate remains intact.

Required composed tests: genuine canonical consumed and superseded settlement retire a returned unknown direct issuer; inject interruption before effect entry, after effect but before returned persistence, after returned persistence before readback, and after retirement commit before reply. Show running remains blocked even with a genuine consumed proof, whereas a restarted owner can retire durable returned with that exact proof; preserve pending/live issuers and wrong event/attempt/key/claim/canonical proof without metadata clearance. Canonical proof replay after reconciliation admission ended remains idempotent and can settle a matching later-returned issuer; original direct token cannot write again. Explicit current-generation retry after verified supersession uses the accepted original/replacement target once, while the original selector does not resend. No installed/native no-writer proof is inferred from these controlled source tests.

## Supported protected reconciliation, without proxy identity

`ace-herdr inbox reconcile` selects the same fixed authority from the read-only entry response, then invokes the EXISTING `reconcile_inbox` RPC from the actual Herdr process through a fixed bounded Herdr transport consumer analogous to existing InboxContextCompletionClient. It does not proxy mutations through the selected child (that would change kernel process identity), import Assign Ruby, or add a new RPC. Existing ProtectedSocket endpoint inode/UID/GID/groups/incarnation checks, canonical one-request envelope and existing inbox_proof multipart encoding are required, implemented under one maintained Herdr transport owner rather than command-local wire assembly.

RPC params remain exactly `{mapping_id,assignment_id,attempt_id,expected_generation,event_id,inbox_context_id,expected_registration,receipt_sha256,signature_sha256,transfer}`. Read the proof and detached signature from stable held regular no-follow nonblocking files, each1..16384bytes; strict signed JSON bytes remain unchanged. Reconstruct expected_registration exactly `{event_id,attempt_id,payload_sha256,receipt_key_sha256}` from signed proof event/attempt/payload_sha256 and the explicit original `--receipt-key-sha256` retained from canonical bind/enqueue registration. Existing signed native proof does NOT contain the receipt-key fingerprint; do not invent that field or substitute the current key. These are untrusted expectations, not registration authority. Endcap compares them with its canonical original inbox_binding and fixed context key, validates signature/native proof, holds context-before-lifecycle/event exclusions, and publishes only the existing canonical reconciliation/import CAS. Changed proof/selectors under the same stable mutation conflicts.

Only actual original launcher or the context's installed supervisor is admitted by the existing kernel/role/purpose owner; workers, signer and observer cannot impersonate authority. The operation's original canonical completion is independently rechecked by InboxContextCompletionClient before the fixed context owner clears in_flight. Lost reply is uncertain and uses original canonical completion recovery; it never calls local Inbox#reconcile, resends native delivery or fabricates an effect binding. Public output is the existing bounded reconciliation projection/replayed metadata. Other source adoption of `ace-assign inbox-reconcile` remains mandatory family work, but is not a prerequisite for this Herdr command's direct existing-RPC join.

The signer remains a genuine separate consumer of observe_to_sign admission/snapshot through accepted downstream completion. No signing CLI or private-key path is introduced. Rotation/paired installer behavior and actual native consumption remain their existing owners' work.
