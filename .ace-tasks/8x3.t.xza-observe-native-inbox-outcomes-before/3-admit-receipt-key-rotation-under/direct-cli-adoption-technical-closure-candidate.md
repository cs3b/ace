# Direct Inbox CLI adoption — technical closure candidate

Draft for independent readiness review, based on `623aa67e4`. This resolves the three decisions in `direct-cli-adoption-review-input.md`; it does not promote xza.3, implement interfaces, or claim installed acceptance. Existing admission, rotation and canonical reconciliation checkpoints remain valid within their recorded limits.

## Observable supported flow

Protected `ace-herdr inbox enqueue`, `deliver`, `status` and `reconcile` use authenticated installed selection before constructing any local Inbox or reading payload/proof files. Enqueue/deliver run in the fixed context owner; reconciliation reaches the existing protected authority operation. Standalone callers retain existing local behavior only after trusted classification says ordinary. Unsupported protected roles, unavailable selection and unknown effects refuse without local fallback. Refusal alone does not satisfy this adoption task: all positive flows below must execute.

Examples (existing `inbox` namespace, JSON output):

```text
ace-herdr inbox enqueue --project PROJECT --mapping MAP --inbox-context CONTEXT \
  --event EVENT --attempt ATTEMPT --ref reverse.json --file payload.txt
ace-herdr inbox deliver --project PROJECT --mapping MAP --inbox-context CONTEXT \
  --event EVENT --attempt ATTEMPT --claim-generation 0
ace-herdr inbox status --project PROJECT --mapping MAP --inbox-context CONTEXT \
  --event EVENT --attempt ATTEMPT
ace-herdr inbox reconcile --project PROJECT --mapping MAP --inbox-context CONTEXT \
  --assignment ASSIGNMENT --attempt ATTEMPT --event EVENT --receipt proof.json \
  --mutation MUTATION --expected-generation GENERATION --receipt-key-sha256 ORIGINAL_KEY_SHA
```

Selection, assignment, attempt, event and mutation IDs use their existing bounded colon-free token rules; operation IDs retain their existing fixed hexadecimal rule. Reverse Ref session/pane values retain the existing Ref token and native address rules, which allow colons; do not apply the selection/event ID restriction to them. `claim-generation` and authority `expected-generation` are distinct strict nonnegative integers. All protected selectors are required and hints must agree exactly with explicit arguments. No endpoint/store/key path, actor, UID, force, generation refresh or completion boolean is accepted. Existing standalone options are unchanged; protected-only options in a genuinely uninstalled ordinary environment refuse.

## One immutable discovery owner, with no package cycle

Reuse `Ace::Runtime::Molecules::ProtectedTaskContextEntry` and its existing fixed `/etc/ace/task-context-entry.json` discovery. Its closed schema remains `{schema,task_context_entry}`, schema `ace.protected-task-context-entry-selection/v1`; entry pin remains exactly `{manifest,wrapper}`, each existing `{path,bytes,sha256}` reference. No second discovery pointer, permission projection or mutable grant map is added.

Lab Assembly/Startup and the SAME LabNativePublication transaction remain the sole producer of that immutable entry manifest/wrapper and publication projection. Their existing bootstrap/source/preparation/runtime proof is required. Expand only the source-owned protected command allowlist for the two read-only modes below. A current publication chooses trusted reader code; it does not choose an event's historical key, authorize native effects or grant a caller role. The accepted entry remains held through each invocation, using the existing descriptor-passed interpreter and manifest, bounded subprocess, empty environment and exact selected wrapper bytes; never PATH, an environment-selected executable, or a reopened wrapper pathname.

Herdr already depends on Runtime and owns BoundedProcess. It may use these existing boundaries to invoke the selected Assign child; it does not import Assign Ruby or add an Assign gem dependency. The child alone interprets Deployment/DeploymentHistory and uses the SAME `ProtectedAssignmentContext#protected_participant?` being implemented for attempt CLI adoption. That classifier includes all explicit current and retained project role UID arrays, authorities[].uid, context owner_credentials.uid, receiver executor_uid and mapping launcher/worker UIDs. It is an exhaustive refusal boundary, not role permission. This shared source owner must land before positive adoption; no second classifier in Herdr.

New source-selected child modes:

* `authority inbox-context-principal`, no arguments: one compact JSON line, exactly `{schema,uid,protected_participant}`, schema `ace.assign.inbox-context-principal/v1`, at most1024bytes. UID must equal the actual Herdr caller UID; boolean is classification only.
* `authority inbox-context-selection --project PROJECT --mapping MAP --inbox-context CONTEXT`: one compact JSON line, exactly `{schema,uid,project_id,mapping_id,inbox_context_id,descriptor,history,context,authority}`, schema `ace.assign.inbox-context-selection/v1`, at most16384bytes. descriptor/history are exact held installed immutable `{path,bytes,sha256}` refs. context is exactly `{control_socket_path,owner_credentials,native_mapping_id}`; owner_credentials is `{uid,gid,groups}`. authority is exactly `{authority_id,socket_path,uid,gid,groups}`. IDs/credentials/path bounds use existing Deployment validation. No store/key/private path or grants leave this response.

The child loads and holds current descriptor/history via existing owners, requires history selects current descriptor, resolves the exact project/mapping/context association and matching authority, and verifies the selection unchanged before replying. It does not call authority-only `verify_inbox_context!` as an unprivileged caller and does not inspect private journal/Inbox files. Actual client endpoint authentication and owner authorization remain mandatory afterward. Retained participant with removed current mapping/context refuses. No selection response is accepted from ambient config or another command.

When discovery is absent, Runtime's existing presence checks against installed descriptor/history/publication still force refusal. When discovery exists, classification runs even without protected flags, before file reads or local construction. Entry failure/malformed output/ref drift is refusal; no ordinary fallback. Only genuinely absent installation plus no protected hints, or successful trusted ordinary classification plus no protected hints, permits local mode. Discovery/selection pins live only within the held operation; every new command reselects and authenticates current owners. The context endpoint receives the ACTUAL Herdr process kernel peer, not the selected child's PID or a forwarded UID grant.

## Fixed context effects and bounded ingress

Reuse InboxContextServer/Client and InboxContextOwner's source-selected Inbox. Add fixed `enqueue_context`, `deliver_context` and `status_context` operations; no arbitrary callbacks, executable selection or target filesystem paths. Existing purpose/role grants remain authoritative: source context owner checks actual peer UID/GID/groups/birth and the configured enqueue/deliver/observe purpose. CLI classification never adds a grant.

Enqueue is closed `{operation_id,key_generation,event_id,attempt_id,reverse,payload_bytes,payload_sha256}`. reverse is exactly the existing normalized Ref `{schema,session,pane}`. `payload_bytes` is a strict JSON integer in1..65536 naming the raw byte length, never content; `payload_sha256` is exactly64 lowercase hexadecimal characters. The <=16KiB strict JSON metadata line ends with its existing newline delimiter; immediately afterward come exactly payload_bytes raw UTF8 bytes, followed by mandatory write-half-close/EOF. There is no payload delimiter, second content field or duplicate encoding. Short body, surplus bytes, digest mismatch, invalid UTF8 or NUL refuses before effect entry. Add a bounded one-part ingress using the existing InboxContextWire framing owner; no base64 expansion or caller filename. Ref/payload files use one held regular no-follow nonblocking bounded handle, strict decoded-duplicate JSON for the Ref, stable handle/path metadata and no NUL. File reads occur only after protected selection. Payload remains subject to existing native limits and managed-envelope rules; this CLI does not invent a managed-envelope or target-authority override.

Deliver is closed `{operation_id,key_generation,event_id,attempt_id,expected_claim_generation}` with no raw payload/ref. Status is closed `{event_id,attempt_id}` and read-only; require configured purpose visibility and exact retained attempt association. All metadata/proof decoding remains strict depth16 UTF8 JSON with existing size bounds and extra-byte refusal. One original30s absolute context deadline covers frame/body/reply; it never clears an admission or declares no effect. Public record projections remain bounded and do not expose raw payload/native output/private paths.

The CLI acquires existing `begin_context_operation` for the exact enqueue/deliver purpose/event with its captured actual process binding. It retains returned operation_id/key_generation/fingerprint and calls the fixed effect. Admission precedes inventory/event locks. The owner persists original direct-input binding in the EXISTING operation.effect_binding field before any effect and sets in_flight=1. Extend that field to a closed purpose-discriminated direct binding `{schema,purpose,event_id,attempt_id,selection,input_sha256}` with schema `ace.herdr.inbox-direct-effect/v1`. For enqueue, selection is exactly `{reverse,payload_bytes,payload_sha256}` with the normalized Ref and bounds above; for deliver it is exactly `{expected_claim_generation}` with a strict nonnegative integer. The existing reconciliation binding remains its separate exact shape. input_sha256 is the SHA256 of the existing deterministic JSON encoding of `{purpose,event_id,attempt_id,key_generation,selection}`, taking key_generation from the enclosing retained operation. Retain only these original decoded selectors, not raw payload or an outcome copy; this permits exact resumed readback rather than an unverifiable digest-only claim. No payload, outcome copy or new per-event ledger enters control metadata.

The state validator must discriminate these branches explicitly. A nil effect_binding is allowed only for an admission that has never entered an effect, with in_flight=0 and completion=nil. A direct binding must match the enclosing operation purpose/event, validate its closed schema/selection and recomputed input digest, and have completion=nil; direct completion must not occupy the existing canonical reconciliation completion field. A reconciliation binding keeps its current exact validation and, when in_flight=0, its required verified canonical completion. Do not weaken that existing requirement to accept any idle binding.

For a structurally valid direct binding with in_flight=0/completion=nil, the tuple is only a known-idle candidate, never proof by itself. On resumed begin admission, fixed effect replay and end admission, the source owner must revalidate the retained DeliveryRecord under the existing context→inventory/event lock order before returning idle or deleting the admission. It must recheck exact event/attempt, immutable original payload/normalized reverse/target and the operation's selected key association, using the retained selection and source key owner; enqueue may observe later legal record transitions without rewriting its original association. Deliver additionally rechecks its original expected claim generation against the existing claim/submission-intent/binding state: a read-only older-generation result cannot authorize another effect, and known completion requires the exact source-owned pre-submission refusal or accepted post-operation generation/binding and no unresolved issuer described below. Missing, corrupt, changed or insufficient record evidence refuses and preserves the admission/in_flight/completion metadata; it never silently treats arbitrary idle metadata as effect proof. Only the fixed owner can persist the known-idle transition after its original issuer returns and this readback succeeds. Pure structural validate_state! therefore cannot by itself authorize resumed direct completion.

Owner source effect execution uses the admitted current key from InboxContextKey and `source_inbox!`; no ambient `Inbox.from_config`. It validates event/attempt and immutable target/payload/key association using the existing Inbox/DeliveryRecord owner. Each event is serialized by its existing inventory/event locks. A source-owned in-memory issuer entry prevents concurrent execution for the same operation; exceptions/EOF/deadline never remove durable in_flight. Changing input under a retained operation conflicts. An admission without an effect remains known idle and can be ended; once effect entry is persisted, generic end cannot clear it.

## Positive completion and exact replay from the existing ledger

Enqueue creates the existing queued DeliveryRecord, pinning the admitted key fingerprint. Completion requires exact retained record readback after the write: event/attempt, payload digest, original normalized reverse/target and key fingerprint match the original binding; all writes are durable. Then the owner marks the operation known idle and returns its existing bounded registration/record. A duplicate exact enqueue uses the retained record and cannot create or replace an event. A conflicting request or an old-key event that cannot match current admission refuses without rewriting old fingerprints; status is the historical observation route. If a crash leaves in_flight with no authenticated matching record, retain unknown; absence is not a no-effect certificate.

Protected deliver has an explicit compare-and-effect join on the EXISTING DeliveryRecord claim_generation under its event lock. At generation0 with queued untouched record, expected0 permits the first invocation. Before native submission the existing Inbox owner increments claim_generation and durably persists its existing claim and submission_intent. A replay with an older expected generation returns authenticated retained record only, with no native or wake call. Equal expected generation permits a new invocation only when existing source state is queued and positively pre-submission: no submission_intent, no unknown original issuer and all preceding effects are settled. Future expected generation conflicts. Same event at delivered/completed/uncertain is read-only regardless of expected selector. A deliberate retry after verified pre-submission refusal therefore supplies the returned new generation explicitly; repetition never silently refreshes it.

This comparison must live inside the SAME Inbox event transaction as claim increment, not a status check followed by deliver. Owner can extend the existing source Inbox deliver interface with the internally selected expected generation; no second event lock/controller. The existing submission_intent-before-native-call invariant is unchanged. Saved unknown intent never authorizes native resend. The existing delivered wake-retry convenience must not run on protected replay; a wake effect requires its own source-owned, explicitly selected retry contract and is not delivered by this amendment. A fresh first delivery may retain its existing bounded wake behavior; failure/uncertainty remains recorded.

Known completion means the fixed owner observed its issuer return and revalidated a durable matching post-operation record: queued only with authenticated pre-submission refusal, or delivered/completed with exact accepted binding/generation and no unresolved issuer. It may then clear in_flight, after which the actual original peer explicitly ends admission. The event state still blocks rotation unless completed. Unknown native result, crash during effect, uncertain state or unverified wake retains admission blocked; positive downstream canonical reconciliation or existing reviewed no-writer recovery is required. There is no callback-true clearance, timeout cleanup, caller completion claim or automatic resubmission.

After lost effect/end reply or process restart, exact older-generation deliver inspects only retained DeliveryRecord and outstanding operation metadata. It must not call Inbox#deliver to obtain a replay result, since that method can retry wake. Repeated known enqueue/deliver after end ACK loss can use original immutable record and claim generation without storing a second replay/outcome table. No unbounded completed-operation history is added. Durable unknown admission remains reconstructable and blocks rotation even when a new process reads the event. Clearing an orphan still requires xza.3's existing independently verified original-writer termination/downstream-drain contract; CLI cannot provide that proof.

## Supported protected reconciliation, without proxy identity

`ace-herdr inbox reconcile` selects the same fixed authority from the read-only entry response, then invokes the EXISTING `reconcile_inbox` RPC from the actual Herdr process through a fixed bounded Herdr transport consumer analogous to existing InboxContextCompletionClient. It does not proxy mutations through the selected child (that would change kernel process identity), import Assign Ruby, or add a new RPC. Existing ProtectedSocket endpoint inode/UID/GID/groups/incarnation checks, canonical one-request envelope and existing inbox_proof multipart encoding are required, implemented under one maintained Herdr transport owner rather than command-local wire assembly.

RPC params remain exactly `{mapping_id,assignment_id,attempt_id,expected_generation,event_id,inbox_context_id,expected_registration,receipt_sha256,signature_sha256,transfer}`. Read the proof and detached signature from stable held regular no-follow nonblocking files, each1..16384bytes; strict signed JSON bytes remain unchanged. Reconstruct expected_registration exactly `{event_id,attempt_id,payload_sha256,receipt_key_sha256}` from signed proof event/attempt/payload_sha256 and the explicit original `--receipt-key-sha256` retained from canonical bind/enqueue registration. Existing signed native proof does NOT contain the receipt-key fingerprint; do not invent that field or substitute the current key. These are untrusted expectations, not registration authority. Endcap compares them with its canonical original inbox_binding and fixed context key, validates signature/native proof, holds context-before-lifecycle/event exclusions, and publishes only the existing canonical reconciliation/import CAS. Changed proof/selectors under the same stable mutation conflicts.

Only actual original launcher or the context's installed supervisor is admitted by the existing kernel/role/purpose owner; workers, signer and observer cannot impersonate authority. The operation's original canonical completion is independently rechecked by InboxContextCompletionClient before the fixed context owner clears in_flight. Lost reply is uncertain and uses original canonical completion recovery; it never calls local Inbox#reconcile, resends native delivery or fabricates an effect binding. Public output is the existing bounded reconciliation projection/replayed metadata. Other source adoption of `ace-assign inbox-reconcile` remains mandatory family work, but is not a prerequisite for this Herdr command's direct existing-RPC join.

The signer remains a genuine separate consumer of observe_to_sign admission/snapshot through accepted downstream completion. No signing CLI or private-key path is introduced. Rotation/paired installer behavior and actual native consumption remain their existing owners' work.

## Verification and ownership

Implement the first complete vertical slice as actual registered Herdr enqueue→fixed context owner→original event registration; deliver and reconciliation extend that same flow. Advisory size large due to cross-package producer/consumer joins. Source-owned shared classifier is Assign's owner; selected child modes are Assign; protected_arguments/manifest/projection publication remain Lab Assembly/Startup; direct effects/client/CLI remain Herdr; canonical reconciliation remains existing Endcap/JournalMutation. This contract introduces no additional task/status closure or parallel ledger.

Required actual controlled composition: accepted Assembly generated entry/manifest→Runtime held discovery→selected Assign child→default registered Herdr CLI→real Unix context server/store→actual temporary DeliveryRecord. Inject excluded kernel/native/provisioning observations only. Prove current+retained nonworker classification and missing/corrupt/removed discovery fail before local constructor/input read; unknown role cannot become ordinary. Prove enqueue key pin and changed-input refusal, real event-lock generation CAS, one native submit after lost ACK/restart, exact replay with no wake, explicit new-generation retry only after positive pre-submit failure, mixed-generation rotation races, original-peer end, unknown-admission persistence and no second outcome store.

Reconciliation must execute actual CLI→existing authority Client/Server-equivalent wire→real canonical signature/import/reconciliation/completion path, including genuine accepted original registration; foreign roles/birth, wrong association/key/generation, changed signed bytes, partial uploads, local proof override and CAS/reply loss refuse or stay uncertain with no repair writes. Both effect and reconciliation tests trap caller-local Inbox/coordinator construction. Ordinary local command behavior stays independently tested. No root/native/systemd/process probe is authorized by this drafting contract; installed drills are exclusively central gad.2. Independent readiness review, executed inspected source tests and independent code review precede source integration.
