# Verify Forgejo create provenance and uncertain outcomes

## Outcome and ownership

A Forgejo PR creation receipt proves the requested source and destination, and any unproven result after mutation remains explicitly uncertain. Owner: ace-git-forgejo; shared public surface remains ace-git. qkb.0 consumes the receipt, qkc owns the installed delivery matrix. This is one medium create-lifecycle repair after z78; it neither reopens delivered provider history nor duplicates transport-hygiene task 8x3.t.3zi (IssueApi, fj process cleanup and review-comment paths).

## Verified gaps

Code-path review at ACE `686abe359` found that api_head_argument! reduces a supplied source URL to owner:branch without proving that URL is the owner's actual fork. The successful-create readback checks expected SHA/draft, but not the requested head repository/ref and base ref. A different same-owner fork at the same SHA can therefore yield an accepted receipt. The public PullRequestLifecycle#create passes that receipt through. Separately, the GET after HTTP 201 is outside the unknown-outcome translator: read failure or stale readback can escape as an ordinary pre-mutation error despite a created PR. These are code-path findings, not newly executed reproductions. First implementation tests reproduce both before the fix.

## Behavior and public contract

- Preserve existing ace-git PR create CLI, Provider#create_pull_request, normalized receipts and error taxonomy; no raw provider path in assignment consumers. Resolve the selected server/base repository once and preserve exact requested head_repository_url, head_ref, base_ref, expected_head and draft.
- Before mutation, prove that the API's owner:branch selector will select the requested canonical/fork repository. Same hostname and owner are insufficient. A nonexistent/unrelated/same-owner wrong source, ambiguous fork selection, unprovable identity or wrong server fails closed without a create send. Identity is repository identity under the existing URL normalization rules, not a display name.
- After accepted creation, a success receipt requires authoritative agreement on selected base repository, base ref, source repository, source ref, expected SHA, draft and created PR identity. Missing or contradictory fields never count as success. Concurrent repository/ref/head changes after preflight invalidate acceptance and require reconciliation, even if the commit SHA happens to match another repository.
- Once a mutation might have been accepted, unavailable/auth-failed/malformed/absent/stale/mismatched verification is ProviderUnknownOutcomeError with non-secret selected operation identity and reconciliation context. An accepted 2xx with incomplete creation identity is uncertain, not proof of refusal. Known rejection before application retains the appropriate pre-mutation error category.
- No automatic mutation replay follows uncertainty. Read-based reconciliation reuses exactly one matching authoritative outcome; zero, multiple or mismatching candidates remain explicit unresolved/conflict outcomes. Existing matching-PR idempotency still validates the full requested identity and draft; a lost response cannot authorize another create. Retain attribution/reconciliation in the caller's existing qjl journal; no provider-local ledger.
- Never include tokens or secret HTTP payloads in errors. This task does not change merge/ready behavior, workflow vocabulary, authorization ownership or minimum supported Forgejo version.

## Success criteria and verification

- [ ] SC1: Canonical and same-server fork success receipts bind every field above. An unrelated repository with the same owner, branch and SHA as the owner's real fork is rejected before POST. Cover wrong server, missing repository and ambiguous/unprovable selector identity.
- [ ] SC2: After an accepted POST, change each source/destination/ref/SHA/draft/PR identity field independently; no valid receipt emerges. Include missing provenance and a returned PR in the correct base repo but sourced from the wrong same-owner repository.
- [ ] SC3: Successful send followed by unavailable/auth/404/malformed/stale GET, malformed accepted response, and transport loss all yield unknown outcome with exact reconciliation context. Assert mutation call count remains one; explicit reconciliation adopts only one full-identity match and never blindly retries.
- [ ] SC4: Exercise public ace-git lifecycle and shared provider contracts. Run `bin/ace-test ace-git-forgejo all`, `bin/ace-test ace-git all`, impacted contract tests and `bin/ace-test-suite`; retain source SHA, commands/results and independent review. An authorized disposable Forgejo scenario verifies actual owner:branch fork selection and wrong same-owner source refusal; scripted IO separately covers deterministic response-loss cases. No production endpoint writes are required or authorized by this drafting step.

Usage: `ux/usage.md`. No unresolved behavior decisions; transport/layout choice belongs to implementation planning. Readiness review must precede promotion; provider acceptance precedes qkb.0 acceptance.
