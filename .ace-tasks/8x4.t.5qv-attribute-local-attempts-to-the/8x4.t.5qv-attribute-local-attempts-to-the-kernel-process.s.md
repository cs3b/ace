# Attribute local attempts to the kernel process account

## Objective

Make local attempt ownership agree with the authenticated Unix process account so a legitimate local caller can use HITL without inheriting the terminal login account. This is one standalone, small vertical slice in Assign; installed qjz acceptance remains separately owned by qjz.

## Expected behavior and interface contract

`ExecutionIdentityResolver` with adapter `local` returns the operating-system account name for the resolving process's effective UID. Local attribution is supported only when real and effective UIDs are equal. A mismatch fails with `UnauthorizedIdentity` before an attempt or runtime binding is published. Login-session identity, `USER`, and `LOGNAME` cannot select or rescue the actor.

The effective UID must resolve to a nonempty account name whose account UID matches that UID. Missing accounts, failed lookups, empty names, or credentials changing during resolution fail with `UnauthorizedIdentity`; there is no numeric or environment fallback. The successful actor agrees with the username obtained from authenticated Unix peer credentials for that same process on Linux and macOS.

The existing local coordinator role, local runtime identity, native process ancestry/binding checks, and service-adapter contract remain intact. This change does not rewrite historical attempts or adopt an existing attempt owned by a different recorded actor. Existing ownership checks continue to refuse such access.

No CLI flags or caller-supplied identity fields are added. Developer usage and failure scenarios are in [ux/usage.md](ux/usage.md).

## Success criteria

- [ ] SC1: A process whose kernel account is `mc`, but whose login session or environment names `root` or another account, creates a local attempt owned by `mc` and can access it through the real authenticated HITL Unix boundary.
- [ ] SC2: A valid kernel account resolves even when login and environment names are absent. Invalid account resolution and unequal real/effective UIDs fail before canonical attempt mutation; they do not fall back to another identity.
- [ ] SC3: Existing native binding and service identity regressions remain green. Existing canonical ownership is preserved without history repair or account impersonation.

## Verification plan

Maintain focused resolver regressions for misleading login/environment values, missing login/environment values, missing/empty/wrong-UID account results, unequal real/effective UIDs, and a credential change during resolution. Check classified failure and absence of canonical attempt mutation at the owner boundary. Preserve service-adapter tests.

Exercise a real Unix-socket peer with the actual current account and a real local attempt, verifying resolver actor, authenticated peer username, and ownership access agree. Run focused and affected Assign/HITL verification through checkout `bin/ace-test`. After independent review and integration, rerun the separately maintained installed qjz SC3 scenario against freshly built exact integrated gems; that larger acceptance is not required to invent or weaken this task's identity contract.

## Scope and decisions

Only local account attribution and its refusal behavior change. Service identity parsing, protected launch/authority, transport roles, installer policy, and privilege-transition support are outside scope. There are no unresolved behavioral choices: unequal real/effective UIDs are explicitly unsupported, and all failed authoritative account resolution refuses.

## Provenance and references

The first genuine installed SC3 run failed before proposal creation: `8x45o5`, one test, 20 assertions, one failure, terminal exit 1. Artifacts are retained at `/tmp/ace-installed-sc3/run-c57d819e5a28`; the recorded attempt actor is `root` while its authenticated requesting peer is `mc`. This failure remains an unsuccessful acceptance run. Inspection found local attribution using `Etc.getlogin || ENV["USER"] || ENV["LOGNAME"]`; the native binding itself was genuine.

The parent authorized this focused draft/readiness review before source correction. No existing task was found owning the login-versus-kernel-account defect; the existing session-resilience task covers native binding rather than account selection.

[Apple getpeereid documentation](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/getpeereid.3.html) specifies effective peer credentials captured at connection. [Linux kernel v6.1 socket source](https://github.com/torvalds/linux/blob/v6.1/net/core/sock.c) projects `cred->euid` for `SO_PEERCRED`. These support effective-UID attribution; refusing unequal real/effective UIDs avoids silently accepting unsupported privilege transitions.
