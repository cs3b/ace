# Produce authenticated ordinary fixed merge requests and receipts

## Observable result

An authenticated ordinary project overseer can submit one fixed, exactly bound
merge operation, receive a durable acknowledgment, and inspect the same operation
through a read-only status command after either side restarts. The terminal receipt
is attributable to the exact repository, PR, reviewed head and authorization. An
uncertain effect is never repeated to manufacture a receipt.

This child owns the missing ordinary admission/execution/status producer. A new
child is required because xz9.0 owns the protected fixture/endcap, xz9.1 protected
boundary recovery, xz9.2 protected steering and xz9.3 protected canonical result
maintenance. Expanding any of them would mix ordinary overseer authority into a
protected worker boundary. The protected receiver, its children and its request
schema remain unchanged.

## Authority and maintained public surface — decided

Use an explicit `ordinary-merge` mode of the maintained `ace-lab service
request/status` vocabulary. Do not create a second command pair. This preserves
one discoverable fixed-service vocabulary while the mandatory mode selector sends
the request to a separately configured ordinary receiver and admission policy; it
does not broaden the default local route or protected route. `ordinary-merge` is
valid only for `operation=merge` and never accepts executable, argv, UID, socket,
evidence path, credential path or token selectors.

`ace-assign` canonical attempt/evidence state is the sole queue/effect record. The
ordinary receiver writes the admitted request and subsequent outcome through the
public Assign coordinator API and returns an opaque reference only after that
canonical record is durable. The receiver has no journal, mapping database or
receipt ledger of its own. `ace-assign` owns the shared opaque-reference creation,
resolution and read-only-status primitive; this child owns its ordinary merge
admission and `ace-lab` CLI composition. iy6 may later compose that primitive but
does not own or authorize merge. qkb.1 consumes it; qk0 owns queue/recovery;
`gad.b` installs it and `gad.2` owns installed distinct-account acceptance.

## Closed request contract

The only request form is:

```text
ace-lab service request --mode ordinary-merge \
  --project PROJECT --assignment ASSIGNMENT --attempt ATTEMPT \
  --queue-entry QUEUE_ENTRY --operation merge --input INPUT.json \
  --authorization AUTH_REF --request-id REQUEST_ID
```

`INPUT.json` is exactly this JSON Schema. Both packages MUST enforce `format` and
MUST reject unknown fields at every nesting level:

Repository values are canonical forge repository identities, refs are full forge
refs, and `pr_url` is the normalized URL produced by the selected forge adapter.
`review_evidence.reviewed_head` and every `test_evidence[].candidate_head` MUST equal
top-level `candidate_head`; schema validity alone does not waive this semantic join.

**Canonical request digest — spec ruling r4 (2026-10-12; resolves xz94-review-r1
finding 3, producer/consumer digest-definition divergence).** The immutable
binding is exactly this eight-field object: `project`, `assignment`, `attempt`,
`queue_entry` (the closed command selectors as accepted), `operation` (constant
`merge`), `authorization` (the authorization reference string), `request_id` and
`input` (the complete validated request document, including its review and test
evidence references). Its canonical serialization is: recursively sort object
keys by code point, serialize with a compact JSON encoder (no insignificant
whitespace) over UTF-8, and take the lowercase hex SHA-256 of those bytes as
`input_digest`. The digest covers this full binding, never the input document
alone: byte-identical input under any different selector, authorization or
request ID yields a different digest. This coverage is forced by this spec's own
rules: the terminal receipt embeds all request selectors plus top-level
`request_id`/`input_digest` and the producer must verify every embedded value and
the top-level ID/digest against the canonical admitted record; the replay/conflict
rule turns on "any different command selector, authorization, input byte meaning
or canonical digest"; and exact-head binding makes one merge the binding of one
project/assignment/attempt/queue entry/authorization, not of its input bytes.
The producer computes the digest at admission from the received request and
re-derives it for replay and receipt verification; the qkb.1 consumer re-derives
the identical digest from its recorded binding and validates every acknowledgment,
refusal, status and receipt echo against it. No caller transmits a digest at
admission; the `status --input-digest` selector and every echoed digest must equal
this canonical value. Admission authenticates the calling project
overseer against the installed project/receiver mapping, resolves the named queue
entry and attempt, and revalidates authorization, repository/PR provenance,
candidate/base heads and current review/test evidence. A request ID already bound
to the identical digest returns the original acknowledgment/status; reuse with any
different field refuses before effect. Missing, extra, caller-selected execution or
protected mapping/scope/service/generation selectors refuse before effect.

The commands explicitly adopt the maintained `ace-lab` outer envelope: success is
outer `status:"ok"` plus `data`; refusal is outer `status:"error"` plus `error.code`.
This permits the existing CLI emitter and callers to retain one parser instead of an
ordinary-only outer protocol. Successful admission returns exactly:

```json
{"status":"ok","data":{"schema":"ace.lab.service.ordinary-merge-ack/v1","type":"accepted","request_id":"<request-id>","input_digest":"<64-lowercase-hex>","reference":"<opaque>"}}
```

Both outer and `data` objects reject unknown fields. `request_id` and `reference`
are strings of 1..256 characters; `input_digest` matches `^[0-9a-f]{64}$`; no field
is nullable. `reference` is receiver-issued and names the canonical Assign record.
Clients may persist and echo it but may not parse it or derive paths from it. No
acknowledgment is accepted until the request is durable.

Every request-call refusal uses exactly this envelope; both objects reject unknown
fields, `request_id` is a non-null string of 1..256 characters, `input_digest` is
either a lowercase SHA-256 string or null when canonicalization failed, `message`
is a sanitized non-empty string of at most 512 characters, and no `reference` is
present:

```json
{"status":"error","error":{"schema":"ace.lab.service.ordinary-merge-refusal/v1","code":"<closed-code>","message":"<sanitized-message>","request_id":"<request-id>","input_digest":null}}
```

The closed `error.code` set and exhaustive pre-effect mapping are:

| `error.code` | Required pre-effect cases |
|---|---|
| `ordinary_merge_invalid_request` | Malformed/non-object JSON; any request-schema type, format, pattern, required, nullability or unknown-field failure; invalid command selector; operation other than `merge`; method other than `merge`; any executable/argv/UID/socket/evidence-path/credential/token or protected mapping/scope/service/generation selector |
| `ordinary_merge_unauthenticated` | Missing, expired, unverifiable or wrong mutually authenticated caller identity before an ordinary principal is established |
| `ordinary_merge_forbidden` | Authenticated principal is not the configured ordinary project overseer; ordinary authority attempts the protected route; protected authority attempts ordinary merge |
| `ordinary_merge_selection_mismatch` | Project, assignment, attempt, queue entry or installed ordinary receiver mapping is missing, ambiguous or does not match the authenticated principal and original queue record |
| `ordinary_merge_authorization_invalid` | The authorization decision or reference is invalid for this request: missing, expired, revoked, out of scope, or bound to another operation/project/PR/head; a decision that is not an ordinary-merge authorization decision (shape mismatch) also uses this code |
| `ordinary_merge_provenance_mismatch` | The request's forge instance, PR identity, repository or ref identity differs from the bound provenance, including the same SHA in another repository or a different registered checkout/worktree/branch; authorization-decision mismatches never use this code |
| `ordinary_merge_target_changed` | Candidate head, base head or remote target moved from the immutable request before claim/effect |
| `ordinary_merge_evidence_invalid` | Review/test reference is absent, untrusted, stale, non-passing/non-approved, digest-invalid or bound to another head |
| `ordinary_merge_request_conflict` | Request ID already exists with any different command selector, authorization, input byte meaning or canonical request digest (per the canonical request digest ruling) |
| `ordinary_merge_unavailable` | No authenticated receiver response is obtainable before acceptance because endpoint/configuration/startup/deadline failed |

All codes except `ordinary_merge_unavailable` are authenticated receiver refusals
that prove no effect began. `ordinary_merge_unavailable` is a caller-side blocker,
not proof of refusal and never authorizes resubmission. Lost output after durable
admission is unconfirmed/uncertain, never mapped to a refusal code. Pre-admission
refusal is returned only by `service request`, has no reference, and is NOT a
read-only status value.

## Closed read-only status and terminal receipt

The sole lookup form is:

```text
ace-lab service status --mode ordinary-merge --reference REFERENCE \
  --request REQUEST_ID --project PROJECT --assignment ASSIGNMENT \
  --attempt ATTEMPT --queue-entry QUEUE_ENTRY --input-digest SHA256 \
  --format json
```

All selectors are required and must match the canonical record. Status authenticates
the observer and performs no dispatch, retry, authorization refresh or selector
repair. Its success envelope has exactly outer `status` and `data`; outer status is
`ok`. `data` has exactly `schema`, `state`, `reference`, `request_id`,
`input_digest`, and `receipt`; `schema` is
`ace.lab.service.ordinary-merge-status/v1`; `state` is `pending`, `uncertain`,
`succeeded`, or `failed`; the three string identifiers are non-null with the same
bounds/patterns as acknowledgment. `receipt` is null for pending/uncertain and the
exact terminal schema below for succeeded/failed. No `refused` state exists.
Unknown/mismatched references return the maintained error envelope with
`ordinary_merge_selection_mismatch` and no reference, without revealing whether
another project has that reference; other status-call input/auth/unavailability
failures use the matching closed code above. Status-command errors have the exact
same outer/nested keys, types and nullability as the request refusal envelope except
that `error.schema` is `ace.lab.service.ordinary-merge-status-error/v1`; they are
command errors, not reference-bearing durable states or proof that an admitted
effect was refused.

A terminal receipt is embedded, never flattened: all command selectors and the
complete validated input document live under the single `request` object. No
request-selector key is flattened at receipt top level; `remote_observation` uses
distinct observation keys whose values are joined back to that embedded request.

matches the canonical admitted record. Success additionally requires
`forge_instance`, `pr_identity_url`, `target_repository_identity`,
`target_ref_observed`, `merged_candidate_head` and `admission_target_head` to equal

match the installed receiver's registered execution identity; `merge_commit` must
equal `resulting_target_head` for the fixed merge method. Failure is terminal only
with the immutable `no_effect_evidence` proving no merge occurred; every unproved
outcome is `uncertain` with null receipt. Logs, process exit, a SHA without
repository identity or a caller-authored file are never receipts.

## Failure, recovery and rollback

Lost acknowledgment, requester restart and receiver restart reconcile only by the
original request binding/reference and perform at most one merge. Unavailable
pre-admission receiver is a blocker, never a proven refusal. Disconnect after
admission or after effect start stays pending/uncertain until canonical evidence
proves one terminal outcome. Only a proven pre-effect refusal permits a new reviewed
request. Confirmed remote merge with stale local state returns `already_merged`;
qk0 schedules local synchronization rather than dispatching merge again.

Rollback disables new `ordinary-merge` admission in installed configuration while
preserving canonical records and read-only status for every accepted reference.
It stops the ordinary receiver only after in-flight records are terminal or
explicitly uncertain. It never redirects ordinary callers to local execution or the
protected receiver and never deletes an Assign record to permit replay.

## Receiver and executor lifecycle — normative (2026-10-12)

The producer/consumer pair above is incomplete without the execution side.
This section normatively names the RECEIVER/EXECUTOR lifecycle implemented in
`ace-lab` (one commit with this section); without it installed gems cannot
autonomously merge.

**Serve entrypoint.** `ace-lab service listen --mode ordinary-merge --project
PROJECT --config CONFIG` binds the configured unix socket from the
project-scoped, deployment-owned receiver configuration file and serves the
OrdinarySocket SERVER side — the exact bounded framed JSON protocol the PR48
client speaks, with the same handshake and wire bound. Authentication is
mutual through SO_PEERCRED: every connection's peer UID must equal the
configured producer principal UID, and the listener runs as the configured
receiver UID — the identity the client verifies on its side. Every identity,
framing, deadline, parse or bound violation is fail-closed: the peer receives
the closed refusal envelope (or the connection closes) and nothing is ever
dispatched. A single owned lock file excludes a second listener; only the
listener's own endpoint inode is ever removed. No HTTP transport, no host
bridge, no caller-selected endpoint exists.

**Executor lifecycle.** On an authenticated submission the receiver: verifies
the exact selector set (any unknown/protected selector refuses as
`ordinary_merge_invalid_request`); binds project/receiver/principal and the
configuration digest to its installed mapping (`ordinary_merge_selection_mismatch`
otherwise); re-derives the canonical request digest (ruling r4) from the
embedded document and refuses any mismatch; validates the closed request
schema and its semantic joins; resolves the authorization through the scoped
resolver below; verifies the pre-effect target against the configured
canonical repository (candidate object present, base head equal to
`expected_base_head` — a moved target answers `ordinary_merge_target_changed`
before any effect); then admits durably through the public Assign coordinator
API and returns the exact acknowledgment only after that record is durable.
After the acknowledgment is on the wire the executor runs the lifecycle: the
single `pending -> uncertain` CAS (`begin`) is the at-most-one-merge proof;
the effect itself is ONE atomic ref compare-and-swap
(`git update-ref <base_ref> <candidate_head> <expected_base_head>`), so
concurrent writers can never both move the ref and the loser provably
performed no effect; settlement is one journal CAS validated against the
closed receipt schema. A record already uncertain (a lost lifecycle) is
NEVER re-executed or resubmitted — it reconciles only by the original
reference. On receiver restart the listener adopts exactly its own still-
pending records (matching receiver identity and configuration digest) and
drives each to one terminal state; uncertain records stay uncertain. A
failed settlement is terminal only with the executor-owned no-effect
attestation file inside the canonical repository (structured, SHA-256-bound
to the request), matching the journal's no-effect-intact verification.

**Assign receipt production.** The receiver writes through the public Assign
coordinator API only (`admit`/`begin`/`settle` plus read-only record/status):
the admitted request, the claim transition and the exact terminal receipt
live solely in the canonical Assign attempt/evidence journal. The receiver
has no journal, mapping database or receipt ledger of its own. The terminal
receipt is what wakes the queue owner; logs, process exits and files outside
the journal are never receipts.

**Merge-method contract (ff-only).** The closed schema admits literal
`method=merge`; the installed executor defines that method as
FAST-FORWARD-ONLY: the candidate head must be a descendant of the current
base head. A non-fast-forwardable candidate is never merged silently and
never falls back to a merge commit — it answers in the existing
moved-target/needs-rebase refusal family (`ordinary_merge_target_changed`
pre-effect), which is the typed outcome the queue owner maps to rebase +
renewed evidence. Under this strategy the terminal receipt records the
actual strategy executed and the post-merge main sha through its closed
join: `merge_commit == resulting_target_head == merged_candidate_head ==
candidate_head` — that equality IS the receipt's fast-forward proof, and
`resulting_target_head` is the post-merge main head. Any future non-ff
strategy (merge commits, squash, rebase-merge) is a SEPARATE reviewed
contract extension with its own schema/receipt evolution — never an
implicit substitution.

**Scoped decision/admission resolver.** The exact root YAML authorizations
become natively executable inside the receiver through a project-scoped
resolver: the deployment-owned authorization file remains the sole source of
truth, and the receiver resolves one per-request authorization selector
against it — ordinary-merge decision shape, exact binding match on every
closed key (operation, project, assignment, attempt, queue entry, digest,
forge/PR/repository/ref identity, candidate and base heads), and expiry —
returning typed decisions within the existing refusal-code family
(`ordinary_merge_authorization_invalid`). There are NO wildcards, defaults,
prefix grants or broad grants: a decision authorizes exactly one bound
request and nothing else, and only `operation=merge` decisions resolve at
all. Host config/deployment of the resolver's policy file stays post-review
(`gad.b`/`gad.2`); this clause makes the authorization executable, not
broader.

**Configuration surface.** One explicit project-scoped YAML file owned by
the host supplies: project, receiver_id, socket_path, receiver_uid,
principal, principal_uid, canonical repo_path, policy_path and the execution
identity (checkout/worktree/branch). The loader validates the exact closed
shape and fails closed; it invents no credential and accepts no
caller-selected value. In-package executable acceptance proves the loop
request → authenticated admission → real fast-forward merge on a sandbox
repository fixture → terminal receipt in a fixture Assign journal → read-only
status resolves → the next request advances — entirely without host chat;
real distinct-account installation and boundary acceptance remain
fixture-gated/host-owned (`gad.b`/`gad.2`), skipped-with-reason rather than
fabricated.
