# Steer protected attempts through their canonical runtime owner

## Behavioral specification

The Captain can send direction to, or request stopping, one exact protected
assignment attempt without giving Overseer direct pane/PID authority. qk0 owns
the user-facing CLI and roles; this child owns the generic protected owner API
and its existing mapped native driver. No second controller, journal, launcher
account or domain daemon is introduced.

### Public contract

The protected owner exposes `prompt_attempt` and `stop_attempt`, taking mapping,
assignment, attempt, expected generation and caller-persisted mutation identity.
The caller supplies no pane, PID, native socket, executable or process birth.
Only a currently mapped launcher/supervisor with scope authority may request
these operations. The owner derives exact native/process binding from accepted
09j origin and revalidates generation and current principal at admission.

The authority does not acquire a native socket ACL as a shortcut. The existing
mapped launcher/supervisor driver performs the owner-admitted native operation
against the pinned server and exact original target. Admission and observations
remain in the existing Assign lifecycle exclusion and canonical journal.

Prompt text is nonempty UTF-8, at most 16 KiB, carried as a bounded ephemeral
payload, with only content digest/byte length and operation binding in journal
and sanitized diagnostics. It never supplies credentials or policy. No raw
content is persisted for retries. Native acknowledgement means submission,
never proof of agent consumption or successful completion; native consumption
remains xza-owned. Unsupported/busy/replaced targets refuse before dispatch.

An immutable mutation identity binds caller, action, attempt, generation and
prompt digest. Exact retry returns the recorded current outcome; changed reuse
conflicts. Native issuance is durable before the one effect. A lost reply or
crash cannot silently retransmit the prompt or repeat destructive control.
Uncertain outcome remains visible with the exact binding and recovery action.

Stop records intent, stops new conflicting dispatch through the same lifecycle
owner, and requests termination through the existing mapped native driver.
Already-issued service effects remain separately attributable and uncertain
until their executor reports an accepted outcome. A pane disappearing, a child
pidfd becoming readable, a signal exit code, or deadline alone does not prove
all descendant writers stopped. `stopped` requires current accepted proof for
the exact execution scope, including no surviving writers; otherwise return
`uncertain`, retain ownership/worktree and expose required reconciliation.
No stop manufactures a success receipt or review approval, clears a pending
effect, or authorizes prune.

Public outcomes are `submitted` for acknowledged prompt submission, `stopped`
for a proven stopped scope, `uncertain` for unresolved issued control, and a
typed refusal for stale binding, missing authority, unsupported native capability
or unavailable evidence. Status returns the same canonical mutation identity
and evidence references after restart. Completed attempts cannot be steered;
historical exact retries report retained outcomes without another native call.

### Success criteria and verification

- [ ] SC1: An installed protected assignment receives one bounded prompt via
  owner admission and the actual mapped native driver; exact retry does not
  send twice, and submission is not reported as consumption.
- [ ] SC2: Stop reaches truthful canonical stopped/uncertain outcome; real
  child/descendant, native target replacement, delayed service completion and
  concurrent finish/recovery cases cannot free ownership or permit unsafe prune.
- [ ] SC3: Lost reply before/after native issuance, owner/driver restart, stale
  generation, changed mutation binding, revoked scope and wrong kernel principal
  each have executed tests. No raw prompt appears in durable journal/logs.
- [ ] SC4: qk0 can use these public APIs without importing private native
  implementation or maintaining another registry. Tests and independent review
  cover the final frozen source plus installed distinct-user native flow.

### Readiness questions and safe defaults

Before promotion, review must identify the actual supported native submission
refusal/acknowledgement behavior. Trustworthy installed execution-scope no-writer
proof is now owned by real upstream draft prerequisite 8x4.t.9c2, extracted from
this child. This child consumes that proof for stop; it does not implement a
second scope owner. 9c2 depends only on 09j, not xz9.0 or this child, avoiding a
finish/stop dependency cycle. Current 09j exact-child proof remains insufficient.
The native scope mechanism is unselected and positive stopped is incomplete.
Unsupported
capability defaults to refusal, unresolved issued control to retained uncertainty.

This is a medium advisory-sized child of xz9, dependent on accepted 09j and
xz9.0 owner composition. It does not depend on qk0, qkb, R2/R3 or Lab acceptance.
qk0 consumes it before protected steering acceptance. Local standalone behavior
is explicit and cannot substitute for the protected verification above.

### Provenance

Discovered during qk0 consumer planning on 2026-10-05: Endcap covered
finish/recover/inbox/status but neither prompt nor stop. The existing runtime
pane operations do not themselves provide protected assignment authorization.
This task makes that missing observable result explicit rather than treating
09j launch completion as proof that all consumer controls already exist.
