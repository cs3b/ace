## Required clarification: bind native creation provenance explicitly

09j spec lines 51–69 maps an immutable native target and sends fixed bootstrap argv; lines 133–138 match gate peer to independently observed native pane/child. It does not explicitly define the trust-bearing creation response or prohibit recovering an unknown creation by label/current-pane/foreground lookup. The worker is native-server UID and can access the unrestricted native socket, so Yama2 alone cannot distinguish arbitrary native-created worker processes from the selected bootstrap. Avoid leaving the origin selection algorithm to implementation.

No labels, aliases, focus/current target, caller-provided pane ID, reusable/restored pane or search/adoption after unknown/lost creation response. Unknown creation retains reservation uncertainty and may not release/retry spawn. Same-ID lifecycle guarantees must be validated for the pinned backend, including close/move/replacement/restoration and any runtime respawn. If implementation cannot establish this native-origin guarantee, fail unsupported; any alternative executable attestation or enforced LSM launch policy must be selected and independently reviewed, not replaced with argv/name claims or broad CAP_SYS_PTRACE.

This is a narrow spec clarification, not a proven exploit against the fresh-pane design. The earlier possible same-pane layout replacement hypothesis is NOT confirmed: upstream layout.apply always creates a fresh tab/pane; caller LayoutPane.pane_id is not used to choose the new process. Its tab replacement closes old tab and keeps new pane identities. agent.start writes shell input and requires an available shell; fixed gate ignores terminal input. Initial Linux layout-created panes do not auto-respawn shells; the respawn flag is assigned by restored-session handling. Fresh public pane numbering advances monotonically in a live workspace. These facts support the proposed creation-provenance decision without granting observer CAP_SYS_PTRACE or introducing a broker.
