# Launch a gated worker through authenticated cross-user runtime

## User experience and expected behavior

Input: a mapped launcher requests one managed assignment scope for a fixed
project, worker account and installed native runtime. Process: ACE records an
authoritative reservation, creates a real gated child through the authenticated
runtime control boundary, verifies exact worker UID/PID/OS birth/native session,
binds process-start, then releases that same gate once. Output: qjl attempt ID,
generation and native/process binding, or refusal/uncertainty preserving ownership.

Launcher, authority and worker use distinct accounts in positive acceptance.
Worker cannot reserve/register its own privileged attempt or impersonate launcher.
Native processes execute directly as the installed account. No setuid/runuser/
sudo path, labd, root broker or domain authentication daemon is introduced.

## Interface and ownership contract

Produce the generic launch-origin part of the companion protected assignment
authority contract: authenticated assignment registration, reserve_attempt,
record_launch, bind_process, release_launch and abort_launch. Its kernel-peer roles, mutation/
generation replay and exact child facts use the same protected qjl. This task
owns their runtime/gate integration and the generic authenticated transport needed
for these operations. xz9.0 consumes this launch origin in the candidate review/
service effect endcap; this prerequisite never depends on the future full xz9.0
receiver/import implementation.

Public runtime launch/control takes deployment mapping ID, registered assignment/
scope and authority-issued launch ticket. Result contains attempt_id, launch_ticket,
generation, gated-child native/process binding and classified launch state. The
native transport is the deployment-mapped Herdr v0.9.3 Unix socket with narrow
connect/traverse ACLs. The retained Linux probe proves cross-UID control and
independent child observation; it does not prove a gated launch or product acceptance.

Root-installed mapping binds project, launcher_uid, worker_uid, authority_id,
fixed worker executable/argv, runtime owner UID, endpoint transport/address,
immutable native target and supported backend version. Source owns endpoint
selection/authentication, exact peer/endpoint/process checks, bounded lifecycle,
timeout/reconnect and gate control. Caller cannot choose an endpoint, executable,
UID, credentials or state path. Cwd/environment/project cascade cannot override
the map. Fixed native control uses structural argv/input, never user text commands.

lab-config gad.8 installs accounts and narrowly scoped parent-traverse/socket
read-write ACLs for the mapped launcher only. It owns real deployment proof and reapplies
connect permissions after native server restart because Herdr creates its socket
with mode 0600. A connect ACL grants no write/rename to endpoint ancestors,
authority config/state, or another account's private roots. Endpoint ownership/
inode and native process birth are verified before and after connecting; a
changed inode, owner, peer PID/birth, version or missing ACL refuses control until
the installer has re-established and verified the mapped endpoint. On Linux,
SO_PEERCRED must report the mapped server UID/PID; the launcher independently
reads child UID/parent/PID birth and matches native pane.process_info. Native
layout.apply receives only the installed fixed bootstrap argv. Owner
credentials come from kernel, never HERDR_SOCKET_PATH supplied by worker. No new
authentication daemon substitutes for the existing native runtime.

Reserved children cannot execute payload until canonical bind permission.
Lost replies, deadlines, reused PID/birth, changed native session and launcher
disconnect never release a gate by assumption. Exact bind retry returns the
committed binding; changed identity conflicts. Gate loss must positively terminate
the same child or leave uncertain ownership and explicit supervisor action.
Restart cannot launch a second child for an unresolved ticket. Abort frees
ownership only with positive exact no-execution/no-surviving-writer proof, never
missing history, timeout, failed ps or PID alone.

## Scope, defaults and slice

Standalone real end-to-end gated-launch slice; advisory size large. Includes
the smallest working protected launch origin, native control adapter and public
driver integration. Broader candidate/review import, service dispatch, native
inbox outcomes and domain handlers remain consumers. Existing qjl/runtime APIs
are prerequisites; no reverse dependency on xz9.0 or future installed Lab service
proof is allowed. Existing 16h policy stays unchanged.

Dry-run validates mapping/identity/capability without reserve/spawn/release. Status
is read-only and reports binding/uncertainty without secrets or terminal output.
No force bypass; verbose/quiet change presentation only. Unknown/empty/malformed
IDs and unmapped projects refuse before spawn. Same-user standalone launch stays
explicit and cannot count as protected cross-user acceptance. Unsupported native
capability fails closed and cannot substitute for the required positive outcome.

## Success criteria

- [ ] SC1: Distinct launcher/authority/worker UIDs produce one actual gated native child; payload executes only after authoritative exact bind/release.
- [ ] SC2: Worker/direct CLI cannot impersonate launcher, replace endpoint/config/ancestors, choose UID/argv or fabricate PID/birth/native-session binding.
- [ ] SC3: Duplicate/lost reservation, spawn, record, bind and release replies cause one child or retained uncertainty; reserved/unbound cannot obtain service authority.
- [ ] SC4: Crash/disconnect before spawn, before record, before/after bind and before/after release preserves ownership; only positive termination/no-execution allows abort.
- [ ] SC5: Public driver uses this boundary; genuine native endpoint/OS authentication and root-installed lab-config permissions survive native restart, with no legacy broker or UID switch.

## Selected native gate contract

Linux protected launch uses a fixed root-installed native bootstrap executable,
not an interpreter loading worker-writable code. Herdr `layout.apply` launches
that argv directly; no launcher descriptor inheritance is assumed. The bootstrap
connects to the existing assignment-authority Unix socket, validates its protected
mapping/endpoint and authority kernel peer, and sends `gate_ready` containing the
launch ticket. The authority authenticates the connecting kernel PID/UID/GID,
reads birth, real/effective UID/GID from kernel status (not /proc directory owner,
which non-dumpable can change), and parent lineage independently, and requires exact equality with
the launcher's independently observed native pane/child binding. Ticket possession
alone and an arbitrary worker process never establish gate readiness. The ticket
is correlation data, not a worker-to-launcher authentication credential.

Creation provenance is mandatory: use only a NEW non-restored single-pane layout.
Pin the fresh workspace/tab/pane identity from the authenticated original
`layout.apply` response and the original server PID/birth/endpoint generation.
Herdr v0.9.3 does not return terminal_id in that response: obtain terminal_id
and the original child PID only by querying that exact returned pane on the same
pinned live server, then independently pin the kernel child birth/UID/lineage
and pidfd before admitting gate_ready. Never select a pane through focus, label,
alias, caller-supplied pane ID, current target or restored/reused layout. Validate
this backend's no-reuse/no-respawn guarantees across close, move, replacement
and restoration; a changed terminal/server/child or missing original pane refuses.
A lost or unknown creation reply leaves the reservation uncertain: no search or
adoption of a possible match, repeat spawn, or release. The fixed original
bootstrap and gate must be established through this native creation provenance;
argv/name claims alone are insufficient. If the pinned backend cannot establish
these guarantees, report unsupported and require a separately reviewed mechanism,
not an implicit executable-attestation or elevated observer fallback.

Deployment must first establish trust in the native server: installer-started
root-owned executable/configuration/ancestors, fixed clean environment, fixed
argv, and a protected installer-written current server PID/birth registration.
Both native socket peer and child ancestry must match that exact server instance.
A worker-started same-UID replacement is rejected even with the expected socket
pathname. Installation refreshes the protected server instance registration and
narrow socket ACL after restart; ordinary clients cannot do so.

Because worker and native server share a UID, executable ownership and socket
credentials alone do not prevent same-UID process injection. Linux protected mode
requires enforced Yama `ptrace_scope=2`, no worker/server/bootstrap effective,
permitted, inheritable or ambient CAP_SYS_PTRACE, and a deployment capability
bounding policy preventing its acquisition (including worker-created namespaces
from gaining privilege over these initial-namespace processes). Root installation
owns this host policy. Bootstrap sets non-dumpable before connecting, closes
unexpected inherited descriptors, ignores terminal input as control, and uses
only its fixed payload argv/environment. Scope2 also covers the startup interval
before that call. Mapped real/effective/saved UID/GID and supplementary groups are
checked; no privilege-changing executable or worker-writable library/config path
is permitted. Missing/unreadable policy, changed server birth, capability policy
or insecure artifact refuses before reserve/spawn. This is a new mandatory Linux
deployment requirement, not a claim that current Lab already enforces it.
macOS remains unsupported for protected launch until an equivalent executed
process-injection and identity policy is independently admitted.

`gate_ready` is a restricted worker-role operation on the same authority service:
it cannot register/reserve/bind/release/abort or create service authority. One
connection per exact ticket/child is retained; mismatched/duplicate peers refuse.
The authority checks the canonical recorded binding before acknowledging ready.
`bind_process` remains launcher-only and commits running binding without sending
release. Launcher then calls `release_launch(attempt_id, launch_ticket,
process_binding, expected_generation, mutation_id)` after observing canonical
bind. Authority verifies exact live gate/child and exact live launcher identity,
commits a qjl launch-release-issued fact before sending the single framed release
on the retained authenticated gate connection. All release facts and dedupe live
in qjl, never a second ledger. Exact release replay returns its canonical issued
state and never sends another release. Changed identity/generation conflicts.

Bootstrap accepts one exact bounded versioned release frame for its ticket and
binding; it closes the control descriptor and execs the fixed payload in the same
PID/birth. Partial/malformed frames, gate EOF or 30s deadline exit without payload.
It never reconnects after an established gate stream disconnects. Authority can
reconnect its launcher/native query clients, but cannot recreate a child or gate
for an unresolved launch ticket. Ready reply loss may be reconciled through the
retained exact stream; loss of that stream requires termination/uncertainty.
A lost release reply or EOF after release issuance cannot prove no execution:
release may already have reached the child. Status distinguishes bound-gated,
release-issued and uncertain; no replay reports new invocation permission.

Authority observes launcher PID/birth with an exact kernel handle. Before release
issuance, launcher exit closes the gate and triggers exact child termination
inspection; after issuance it records uncertainty/recovery instead of assuming
payload did not run. A death concurrent with release issuance may leave a payload
running and ownership held; no atomic cross-process liveness guarantee is claimed.
Authority crash/stream EOF before release exits the gate; crash after durable
release issuance retains uncertainty even if no reply was received.

Termination uses native `pane.close` on the pinned pane plus a previously acquired
pidfd for the exact PID/birth. Native success is insufficient: pidfd exit proves
that exact process terminated. Before release issuance, immutable gate/verified
policy and exact exit can establish no payload execution; after issuance, positive
no-surviving-writer and attributable outcome evidence is required by ordinary qjl
recovery. Descendant absence must be proven separately when payload may have run.
Missing pane, PID-not-found, timeout, changed birth or dead server alone never
frees ownership. Workers may signal/close panes or send terminal input; these can
cause denial/uncertainty but cannot produce an authority release frame.

Verification adds actual distinct-UID authority/launcher/bootstrap, malicious
worker same-UID ptrace/process_vm_writev/proc-mem attempts against server and gate
including startup, worker-created gate mimic and native input/close, endpoint
replacement, clean bootstrap environment, wrong group/capability policy, launcher
exit, gate EOF/deadline, native reconnect and duplicate/lost release windows.
Protected positive acceptance must execute with the enforced policy; a Yama=0
fixture is primitive evidence only. Every release crash window checks canonical
qjl issued state and harmless payload count; no ambiguous window permits a second
spawn or releases ownership. Source implementation tests and installed policy
proof remain task deliverables, not work performed during this spec review.

## Readiness decision — independent review required

The remote gate mechanism and exact native termination primitive are selected.
Retained evidence proves fixed native gate startup, peer/native PID equality,
pre-release EOF exit without payload, one release and exact pidfd exit after
`pane.close`. It does not prove qjl integration, policy-enforced malicious-worker
isolation, real launcher process death, transport reconnect/crash matrices or Lab
installation. These are explicit implementation/acceptance requirements above,
not remaining product design questions. This amended contract remains draft with
needs_review until an independent reviewer validates the new decisions.
